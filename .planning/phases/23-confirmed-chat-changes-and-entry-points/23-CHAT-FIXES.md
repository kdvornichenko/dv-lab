# Фаза 23: правки чата вне плана

Две правки api по запросу владельца. Коммиты: `15b72e2` (схемы инструментов), `0a36062` (упоминания, набранные текстом).

## 1. Любой ход чата отвечал `provider_unavailable`

**Что было.** Каждый ход модели заканчивался «Model settings are unavailable». Anthropic отклонял запрос с 400 `invalid_request_error` из-за списка `CHAT_TOOLS` (19 инструментов).

**Причина.** У API три предела для схем со `strict: true`. Два из них были известны заранее, третий нашли на реальном API.
- Поле вида `{ type: ['string','null'], enum: [..., null] }` недопустимо: `Enum value 'RUB' does not match declared type`. Так были описаны `currency` в `propose_payment`, `propose_student` и `propose_rate`, `gender`, `tab` и `dialog` у `open_page` и `task` у `essay_feedback`.
- Параметров с union-типом не больше 16 на весь запрос, их было 29. Необязательных параметров не больше 24: если перевести все 29 в необязательные, API отвечает `too many optional parameters (29) ... (limit: 24)`.
- Размер грамматики строгих схем ограничен, и этот предел не документирован. Даже без union-типов и без необязательных полей 19 строгих инструментов дают «The compiled grammar is too large» или «Schema is too complex». По замерам строгими можно оставить примерно 50 свойств, считая без union-типов. С union-типами помещается меньше.

**Что изменено.**
- `apps/api/src/chat/tools.ts`: помощник `nullable` теперь `nullish().transform((value) => value ?? null)`. Отсутствие поля и `null` дают одно значение `null`, поэтому разбор входа и весь код после него не меняются. Помощник `tool()` принимает список необязательных полей. Признак `strict` стоит только у инструментов из `STRICT_TOOLS`: `mark_lesson`, `add_comment`, `propose_lesson_change`, `propose_payment`, `propose_student`, `propose_rate`, `propose_bulk_move`, а также `essay_feedback`. Остальные 11 инструментов не строгие: инструменты чтения, инструменты только с id, `add_note` и `open_page`. Их вход по-прежнему проверяет zod в `runTool`, на ошибку модель получает `invalid_arguments`.
- Необязательными (поле опускается) стали все поля `propose_payment`, `propose_student`, `propose_rate` и `propose_bulk_move`, у которых раньше было `null`, все четыре поля `open_page` и `task` у `essay_feedback`. В enum больше нет `null`. В описаниях вместо «otherwise null» написано «omit». У `mark_lesson`, `add_comment` и `propose_lesson_change` остались поля `['string','null']`, их описания не менялись.
- Итог для строгих схем: 8 из 19 инструментов, 9 union-параметров, 13 необязательных. Ход `/essay` отправляет один строгий инструмент с одним необязательным полем.
- Проверка «значение из текста учителя» (`saidIn` в `changes.ts`) не менялась: она получает те же разобранные значения.

**Отступление от решения фазы 22.** В фазе 22 строгими были все инструменты. Теперь `strict` стоит только там, где он умещается в предел размера грамматики. Чтобы сделать строгим ещё один инструмент, придётся убрать поля в других строгих схемах. Запас по пределу размера не измерен точно. При новых полях и инструментах нужно запускать `chat-tools-schema.mjs` с ключом.

**Чем проверено.**
- Реальный API (тестовый ключ владельца из `.env`): полный `CHAT_TOOLS` без изменений и отдельный список хода `/essay` на `claude-haiku-5-5` и `claude-sonnet-5-5`, `effort` medium. Ответ `end_turn`, без 400. Первая компиляция новой схемы заняла около 36 секунд, повторный запрос около 4 секунд.
- Новая проверка `scripts/dev-checks/chat-tools-schema.mjs` (описана в README). Без сети она проверяет пределы: нет `type`-массива с enum, у строгих схем union не больше 16, необязательных не больше 24, все схемы закрыты. Живой запрос она шлёт, только если есть ключ, иначе печатает `NOT RUN live request`. Ключ не печатается. Результат `CHAT_TOOLS_SCHEMA_OK`.
- `chat-runs.mjs`: проверку «все инструменты strict» заменил проверкой списка строгих инструментов. Вызов `open_page` на день теперь идёт без необязательных полей. Результат `CHAT_RUNS_OK`.
- `chat-changes.mjs` (разделы payment, cards, deletions, essay), `chat-bulk.mjs` (proposal, children, zone), `chat-api.mjs` (runs, calendar, answers, records): все OK.
- typecheck `apps/api` и `packages/contracts` проходит, prettier проходит.

## 2. Упоминание, набранное текстом, не становилось привязкой

**Что было.** Если `/recap @Имя Фамилия` вставляли или набирали без выбора из всплывающего списка, сообщение сохранялось с `mentions: []`. Модель не знала, о каком ученике речь.

**Что изменено.**
- `apps/api/src/chat/mentions.ts`, новая функция `typedMentions`. Список активных карточек она берёт через `listLessonStudents` из модуля карточек. В тексте ищется `@` + отображаемое имя, сравнение по NFC без учёта регистра, самое длинное имя проверяется первым. Перед `@` должно быть начало строки или небуквенный символ, после имени не должно быть буквы или цифры, вхождения не пересекаются. Единицы позиций те же, что у клиента: UTF-16, `start` сразу после `@`, `text` — срез текста как он набран. Учитываются и NFC-, и NFD-длины имени.
- Если имя неоднозначно (активных карточек с таким именем больше одной), привязки нет, и более короткое имя-префикс вместо него не берётся. Архивные карточки в список не входят. Участки, покрытые клиентскими привязками, пропускаются. Общее число привязок не больше `CHAT_MENTIONS_MAX` (20).
- `apps/api/src/chat/actions.ts`. Найденные привязки вычисляются до решения «свободный текст или быстрая команда», так что набранное `@Имя was` работает как быстрая отметка. Они добавляются к клиентским в `mentions` сохраняемого сообщения и в `quickRequest`. Клиентские привязки по-прежнему проходят `validateMentions`, его проверка не изменилась. Серверные привязки через неё не идут: они построены из активных карточек, а их `text` может отличаться от имени регистром. `requestDigest` считается по исходному запросу клиента, поэтому повтор того же `requestId` не превращается в конфликт.
- Дальше привязка работает как обычное упоминание: `Mentioned students` в контексте модели, имена в проверке публикации, подсветка в сообщении.

**Чем проверено.** Раздел `actions` в `chat-api.mjs` на вымышленных карточках `Alex Example 2206`, `Alex Example 2206 Twin` (две карточки) и архивной `Alex Example 2208 Gone`, всё PASS:
- `/recap @<имя в нижнем регистре>, please` без привязок даёт одну привязку с `start` 8, она хранится с сообщением;
- две активные карточки с одним именем не привязываются, короткое имя вместо них не берётся;
- архивная карточка не привязывается;
- клиентская привязка остаётся как есть и не дублируется, соседнее набранное `@имя` привязывается;
- `mail@имя` и `@имяx` не привязываются, следующее `@имя` привязывается.

Фикстуры удалены, в `dvlab_test` нет строк `Alex Example 22%`. Результат `CHAT_ACTIONS_OK`. Разделы `records`, `answers`, `calendar` и `runs` после правки тоже OK.
