## Summary

Master today has no background sync at all. Every `GET /schedule/week`, `GET /today`, `GET /students` and `GET /students/:id` calls Google inside an account-wide Postgres advisory lock (`lease.ts`), inserts a brand-new snapshot (a `google_read_windows` row plus every event row) and bumps `google_connections.snapshot_revision` [VERIFIED: apps/api/src/calendar/reads.ts:22-62, read-store.ts:51-124]. Commands, the overlap check, the dispatch worker and connection control take the same lock [VERIFIED: credentials.ts:134-158, commands.ts:47-111, schedule/calendar-conflicts.ts:320, worker.ts:61,87, connection-control.ts:210]. The lock is a 5-second try-lock that throws `command_pending` [VERIFIED: lease.ts:11-12,29-40], and every edit version embeds `snapshotRevision` [VERIFIED: read-state.ts:35-50], so any read on any tab invalidates every open form. The Phase 25 background sync that the owner wants rewritten lives only on the local `integrate/calendar` branch (sync.ts, watch.ts and 8 extra tables); 25.1 starts from master and does not merge that branch [CITED: integrate/calendar:.planning/REWORK.md R-09..R-14, R-24].

The recommended rewrite: one current-state projection table of Google event instances in a bounded window, filled by a background task per connection that runs a full pass (`events.list singleEvents=true showDeleted=true timeMin timeMax`) and then token-only incremental passes, triggered by push notifications, a poll timer and a nightly full reconcile. Reads become pure SQL with no Google call and no lock inside the window. The week version (`google_sync_state.revision`) increases only when a pass changes at least one stored field. Edit preconditions move from the global revision to the per-event Google `etag` (If-Match, already the write path). Three new tables total (`google_calendar_events`, `google_sync_state`, `google_event_ignores`), versus eight on the integrate branch.

The editing core extends the existing command journal (`google_commands` + stages + pg-boss singleton per connection) with operations for any event (create, update with scope one/following/all, delete with scope) and adds resize to the lesson operations. Plain events need no local domain table: the projection is their model (D-05, D-06). Lessons stay the app's model; inbound Google changes to bound lessons are applied to unmarked occurrences only, which keeps accounting (`loadMarkRows` derives minutes from local rows) frozen for marked lessons. Calendar choice reuses the account-switch path (retire + new connection row) because `calendarId` is part of every FK tuple.

**Primary recommendation:** build in this order: (1) lock split + local OAuth redirect + new tables, (2) sync engine writing the projection, (3) switch every read to SQL, (4) push, (5) inbound apply + Assign/Ignore, (6) event commands + editor/drag/resize, (7) calendar choice. 12 plans, 7 waves.

## Current State Map (question 1)

### How weeks are read from Google now

1. `GET /schedule/week?start=` resolves the week range in the teacher default zone and calls `calendarReads.refreshCalendarRead(context, { kind: 'window', ... })` before reading SQL [VERIFIED: apps/api/src/routes/schedule.ts week handler].
2. `refreshCalendarRead` wraps everything in `credentials.withAccessToken` (the lease), loads all mappings, pages `events.list` with `singleEvents=true orderBy=startTime showDeleted=true` and a fixed fields mask, then reads series contexts and publishes [VERIFIED: calendar/reads.ts:22-56; gateway.ts:411-429].
3. `publishWindow` locks `google_connections FOR UPDATE`, requires `snapshotRevision` unchanged since the read began and the mapping fingerprint unchanged, inserts a new `google_read_windows` row and all `google_read_events` rows, and sets `snapshot_revision = revision + 1` [VERIFIED: read-store.ts:51-72, 87-124]. Nothing is ever deleted (`dvlab_app` has no DELETE on `google_*`) [VERIFIED: packages/db/drizzle/20261012092848_google_calendar_revoke_delete/migration.sql:1].
4. `readCalendarWindow` returns `fresh` only when the in-memory receipt for this very request (WeakMap) matches the latest window row and the connection revision; otherwise `last_known` and writes blocked [VERIFIED: read-model.ts:118-150; read-state.ts:21-29].
5. Today and Students do the same for `kind: 'next'` (one `events.list orderBy=startTime timeMin=now` prefix walk) and Today also for its window [VERIFIED: routes/today.ts:23-24; routes/students.ts refresh calls at handler lines 100 and 130].
6. The web prefetches neighbour weeks and re-reads the week right before every mutation [VERIFIED: apps/web/app/(app)/schedule/_components/use-schedule-week.ts:19-21; schedule-mutations.ts:164-166].

A single malformed event (zero length, start after end) throws `invalid_provider_data` for the whole page [VERIFIED: provider-events.ts:77,81-87], so one bad event blocks the week.

### What the "background sync of Phase 24" is on master

There is none for events. Master has three timers: the command worker sweep every 5 s [VERIFIED: worker.ts:177], connection control (revoke pump) every 1 s [VERIFIED: connection-control.ts:235], and auth housekeeping. The worker's recovery sweep skips `recovery_required` commands with an effect [VERIFIED: worker.ts:127-146], and admission rejects every new command while any command is unresolved account-wide [VERIFIED: journal.ts:166-172; commands.ts:54-55], so one stuck command blocks all edits (R-35).

The 30-second background sync that R-09/R-10 describe exists only on `integrate/calendar`: `sync.ts` runs each account inside `withAccessToken`, reserves a batch, reads the whole collection with `singleEvents=false`, stores full resources in `google_sync_events`, re-reads every window ever opened and publishes a new revision each run [CITED: integrate/calendar:apps/api/src/calendar/sync.ts:31-78, sync-store.ts:54-130, sync-provider.ts:104-146]. Use it only as a reference of what not to do.

### Where the shared lock is and why it breaks week reads

- `createConnectionLease(pool).run(accountId, op)` takes a pooled client, loops `pg_try_advisory_lock(hashtextextended(accountId, 24))` for up to `LOCK_WAIT_MS = 5000` with `LOCK_RETRY_MS = 100`, then throws `CalendarFault('command_pending')` [VERIFIED: lease.ts:11-12,19-41].
- `withAccessToken` holds it for the whole operation, including network calls with 30 s budgets [VERIFIED: credentials.ts:134-158; reads.ts:31].
- Holders: every week/today/students read, command admission (which also re-traverses the week from Google and rejects on any etag difference) [VERIFIED: commands.ts:47-111, 71-89], the overlap check that runs automatically on New lesson [VERIFIED: schedule/calendar-conflicts.ts:310-330], command dispatch [VERIFIED: worker.ts:61], projection apply [VERIFIED: worker.ts:87], consent and revoke [VERIFIED: connection.ts:207,235; connection-control.ts:210,275].
- Effect: while any of these runs longer than 5 s, a week read gets `command_pending`, `refreshCalendarRead` swallows it [VERIFIED: reads.ts:57-61], the page shows `last_known` with writes blocked. Admission gets `command_pending` → 409 to the user.
- `recordFailure` flips the connection to `reconnect_required` / `permission_required` for any `CalendarFault` with those codes thrown by the operation, not only by token refresh [VERIFIED: credentials.ts:98-114,151-157]. Any new watch/sync code must not run under this wrapper (R-08).
- A refresh CAS loss throws `reconnect_required` [VERIFIED: credentials.ts:51-67]; with the lock removed, two concurrent refreshes would disconnect the account unless refresh becomes single-flight.

### How the week version grows

- `google_connections.snapshot_revision` +1 on every published window read, every `next` read and every applied command [VERIFIED: read-store.ts:18-41, 119-122, 168-171].
- Create precondition: `expectedVersion` must equal the current `snapshotRevision` and the week must match exactly by etag [VERIFIED: command-plan.ts:50-70,131-133; commands.ts:63-89].
- Edit precondition: `eventVersion` hashes `snapshotRevision` with eventId/etag [VERIFIED: read-state.ts:35-50]. Any read anywhere (Today open in another tab, neighbour prefetch) makes every open form stale (R-10, R-37).

`google_calendar_events` — current state, one row per `(connection_id, event_id)`, upsert-only plus cleanup:

| --------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------- |

| event_id                                                        | `id` (instance id for recurring instances) | identity, If-Match target                                                                               |
| etag                                                            | `etag`                                     | edit precondition                                                                                       |
| recurring_event_id, original_start (jsonb `GoogleEventTime`)    | `recurringEventId`, `originalStartTime`    | series/occurrence binding; scope "one/following/all"                                                    |
| status                                                          | `status`                                   | cancelled instances hidden, history                                                                     |
| event_type                                                      | `eventType`                                | only `default` is editable as an ordinary event (others shown read-only with reason)                    |
| start, end (jsonb) + starts_at, ends_at (timestamptz) + all_day | `start`, `end`                             | rendering and SQL range queries; all-day instants via `startOfZonedDay`                                 |
| summary                                                         | `summary`                                  | title                                                                                                   |
| color_id                                                        | `colorId`                                  | block color                                                                                             |

This answers R-07 [CITED: integrate/calendar:.planning/REWORK.md R-07]. ### Pattern 2: Sync pass (full, incremental, 410)

- **Query:** `events.list({ calendarId, singleEvents: true, showDeleted: true, maxResults: 2500, fields })`; full pass adds `timeMin = window_start, timeMax = window_end`; incremental passes only `syncToken` and `pageToken`. `syncToken` cannot be combined with `orderBy, timeMin, timeMax, q, updatedMin, privateExtendedProperty, sharedExtendedProperty, iCalUID`, `showDeleted` cannot be false, other parameters must equal the initial request [CITED: docs/google-calendar/articles/v3/reference/events/list.md:52]. `syncToken` with `singleEvents=true` is the documented example [CITED: docs/google-calendar/articles/guides/sync.md:54-66]. Do not reuse `traverseEvents`: it adds `orderBy=startTime` and validates start ordering [VERIFIED: gateway.ts:418-419; read-pages.ts:23-32].
- **Pagination:** `nextSyncToken` only on the last page; every page repeats the same query with the same token [CITED: sync.md:37,47]. Commit nothing until the last page; then one transaction applies the diff and stores the new token.
- **Diff and version:** for each item compare `(etag, status, start, end, summary, color_id, transparency, recurring_event_id, original_start, event_type)` with the stored row; write only changed rows; `revision += 1` once if any row changed or was removed. An idle pass changes nothing. This answers R-10 and SC7.
- **Out-of-window items in incremental passes:** an incremental page can return changes outside the window. Upsert only rows whose `[starts_at, ends_at)` intersects `[window_start, window_end)`; for rows already stored that moved out, delete them. Whether Google limits incremental results to the initial `timeMin/timeMax` is not stated in the snapshot [ASSUMED: A1]. Either answer works with this rule.
- **410:** the token is invalid; drop it, `epoch += 1`, run a full pass; rows not seen with the new epoch inside the window are deleted at the end of the full pass. No lesson row is created by sync, bindings come only from mappings (keyed by Google ids) or explicit Assign, and the projection key is the Google `eventId`, so a resync cannot duplicate lessons [CITED: sync.md:75; VERIFIED: calendar-schema.ts:358 `google_event_mappings_provider_uq`].
- **Bad items:** an item that fails normalization (zero length, unknown shape) is skipped and counted in `issue`, not fatal for the pass (R-11).
- **Window:** recommended `[monday(now) - 8 weeks, monday(now) + 53 weeks)` in the default zone; the nightly full pass re-anchors it (a fresh full pass with new `timeMin/timeMax` replaces the token), which is how the window advances. Numbers are owner question Q1.
- **Cleanup:** nightly full pass deletes rows outside the new window and rows not seen in the new epoch, except rows that have an active mapping (bound lessons): those are kept as the last confirmed Google fact, because `historyEligibility` needs a confirming row for post-cutover lessons [VERIFIED: history.ts:157-179] while marking looks back 366 days (`MARK_LOOKBACK_DAYS`, `packages/core/src/schedule.ts:266`). Bound rows are a small share of all rows, so storage stays bounded. Old tables stop growing because nothing writes them any more (Runtime State Inventory).

### Pattern 3: One task per connection without a shared lock

- Loop: `setInterval(tick, 30_000).unref()` in `sync.ts`, started from `server.ts` like the worker and closed via `Closable` [VERIFIED: server.ts:39-40,102-108 composition].
- Claim: `UPDATE google_sync_state SET claimed_until = now() + interval '2 minutes' WHERE connection_id = $1 AND (claimed_until IS NULL OR claimed_until < now()) AND <due> RETURNING *`. Due = `requested_seq > processed_seq OR next_poll_at <= now() OR next_full_at <= now() OR channel renewal due`. A crash leaves an expired claim that the next tick takes over (survives restart). In-process `Map<connectionId, Promise>` prevents double runs inside the process.
- Publication CAS: the final transaction checks `connection.generation`, `calendar_id`, `epoch` and that `sync_token` still equals the one the pass started from; otherwise the pass is discarded (disconnect, calendar switch, 410 race).
- Access token: `credentials` gets an `accessToken(accountId, signal)` without the lease: single-flight per account in memory, CAS persist as now, and on CAS loss re-read the row and use the winner's state instead of throwing `reconnect_required` [VERIFIED: current behaviour credentials.ts:51-67]. Only a refresh rejected by Google (`invalid_grant`/401 on the token endpoint) may set `reconnect_required`.
- The lease stays only around command dispatch/apply and consent/revoke (Phase 24 D-05 single writer). Reads, sync, overlap checks and admission never take it.
- Poll cadence (discretion, recommended): `next_poll_at = now + 2 min` when there is no active channel (local development, webhook down), `now + 30 min` with an active channel; `next_full_at` = next 03:00 in the teacher default zone. A command apply sets `requested_seq += 1` so the projection catches the confirmed result.

### Pattern 4: Push (events.watch)

- Register: `events.watch({ calendarId }, { id: uuid, type: 'web_hook', address: <APP_ORIGIN>/api/google/notifications, token: random 32 bytes base64url, params: { ttl } })`. Store only the SHA-256 of the token. Default TTL is 604800 s [CITED: docs/google-calendar/articles/v3/reference/events/watch.md:89]. Address must be HTTPS with a valid certificate [CITED: guides/push.md:101-103]. `events.watch` accepts the granted `calendar.events` scope [VERIFIED: calendar-v3.discovery.json events.watch scopes].
- Webhook: new `routes/google-notifications.ts` mounted in `app.ts` before `sameOrigin` (Google sends no Origin; `sameOrigin` returns 403 for a POST without Origin and without `sec-fetch-site: same-origin`) [VERIFIED: auth/middleware.ts:32-42; app.ts:59]. Check `X-Goog-Channel-ID` matches a stored channel and the hashed `X-Goog-Channel-Token` matches (constant time), then `requested_seq += 1` and return 204. `sync` state messages (message number 1) only confirm the channel [CITED: push.md:189,207]. Return 2xx quickly; 500/502/503/504 make Google retry with backoff [CITED: push.md:287]. Rate limit by channel id in memory (R-06).
- Caddy: `/api/google/notifications` reaches api as `/google/notifications` through `handle_path /api/*` [VERIFIED: deploy/caddy/Caddyfile:69-74]. Both `log` blocks must delete `request>headers>X-Goog-Channel-Token` (and `X-Goog-Resource-URI`, which contains the calendar id); today they only strip the query and Referer [VERIFIED: Caddyfile:2-10,26-34] (R-05; the fix exists only on integrate commit 154af3b).
- Renewal: when `channel_expires_at - now < 24 h`, register a new channel (new id), move the old one to `retiring_*`, then `channels.stop({ id, resourceId })` for the retiring one; overlap is expected [CITED: push.md:215-217,307-337]. A failed stop is retried on later ticks and does not block a new channel (R-14).
- Failure isolation: watch and stop errors set `google_sync_state.issue` only; they never touch `google_connections.state` (R-08). Notifications are not 100% reliable; polling and the nightly full pass cover drops [CITED: push.md:351].
- Local development: no public HTTPS, so no channel; the poll covers it. Push can only be observed where a public HTTPS origin exists (owner question Q5).

### Pattern 5: Resolver and the any-event model (question 3)

Order for each projection row, computed at read time in SQL plus a small TS step (no persisted binding column needed):

1. **Mapping** by `event_id`, else by `recurring_event_id` for a series master mapping → lesson binding `{ ref, studentId }` (existing `bindEvent` logic, moved from reading `google_read_events` to the projection) [VERIFIED: event-mapping.ts:276-304].
2. **Pending command** affecting the ref → `transition` binding (existing).
3. **Ignored** (`google_event_ignores` by event id or recurring master id) → plain event, no suggestion.
4. **Suggestion**: `event_type = 'default'`, not cancelled, timed, and `normalizeDisplayName(summary)` equals exactly one active student's `displayName` → plain event with `suggestion: { studentId }`. `normalizeDisplayName = name.trim().replace(/\s+/g, ' ')` [VERIFIED: packages/contracts/src/identity.ts:13-15]; `displayName` is stored normalized [VERIFIED: packages/contracts/src/students.ts:99]. Compare case-insensitively after `normalizeDisplayName` and NFC; duplicates or zero matches give no suggestion. No prefix, first-word or fuzzy match.
5. Otherwise a **plain event** (D-06): title, time, Google color; editable when `event_type = 'default'`.

Markers ("map back by stored id", D-07): app writes `extendedProperties.private` `dvLocalId/dvKind/...` on every insert [VERIFIED: command-result.ts:50-69]. Mappings are the primary map; markers matter only for events whose id is unknown to mappings, which happens when the Google UI splits a series ("this and following" creates a new master). Whether Google copies private extended properties to the new master is not documented [ASSUMED: A2]. If copied, the resolver links the new master as a continuation of the marked series (inbound cut, Pattern 8); if not, it falls to step 4 as a suggestion.

Assign (D-07): a journal command `assign` that patches only `extendedProperties.private` markers on the Google event with If-Match, and on ack creates the local `lessons` row (single) or `lesson_series` row (master whose RRULE passes `recurrenceFields`: one `RRULE`, `INTERVAL` 1, `WKST` MO [VERIFIED: apps/api/src/calendar/recurring.ts:34-57]) plus the mapping row. This keeps `google_event_mappings.command_id NOT NULL` and its FK intact [VERIFIED: calendar-schema.ts:337,350-354] and makes the binding survive `410` and reconnect because it lives in Google. A recurring event that the weekly model cannot represent can only be assigned per occurrence (owner question Q4). Ignore is local (`google_event_ignores`), no Google write.

Conflict with `25.1-UI-SPEC.md` S5 ("No Google write for the binding itself"): the user-visible flow is the same ("Assigning…", then the block becomes a lesson); the difference is an invisible `extendedProperties.private` patch. The alternative without a Google write needs a local binding with no command (`command_id` is NOT NULL with an FK), i.e. a new bindings table or a nullable column, and the binding would not survive a reconnect to the same calendar through Google. Owner question Q7.

Plain events have no local domain table: the projection row is the model, commands target the Google id. Lessons keep `lesson_series`, `lesson_exceptions`, `lessons`, `lesson_marks` [VERIFIED: packages/db/src/schema.ts:215-313].

### Pattern 7: Recurrence scope on Google vs local rules (question 3)

- "This occurrence": Google instance patch keeps `originalStartTime`; locally an exception keyed `(series_id, original_on)` [VERIFIED: schema.ts:241-269]. No standalone insert (Phase 24 D-06).
- "This and following": Google has no single call. It is trim old master `UNTIL` + insert a new master, which is exactly the app's cut (old series `ends_on`, new series row, moved future occurrences become `lessons`) [VERIFIED: packages/core/src/schedule-series.ts:51-76,127]. Existing `move_series` already performs these stages.
- "All events": for plain events patch the master (Google shifts every instance, past included). For lessons never patch the master's time: it would rewrite past instances in Google; use `move_series` from the next occurrence.

### Pattern 8: Inbound apply to lessons and the D-08 boundary (question 7)

Boundary: an occurrence with a mark row is frozen; inbound apply touches only unmarked occurrences. This is sufficient because accounting reads only marked occurrences and derives start/duration from local rows (`loadMarkRows` → `occurrenceAt` / `toSingleLesson`) [VERIFIED: apps/api/src/schedule/rows.ts:298-353]; `deductedMinutes` counts only `done`/`no_show` [VERIFIED: packages/core/src/balance.ts:13-16]. Alternative (not recommended): freeze everything before a cutover date.

| Google fact for a bound event                                  | Local effect (in `schedule/inbound-apply.ts`, under `lockSeries`/`lockLesson`)                                                    |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Single: start/end changed                                      | `lessons.starts_at`, `duration_minutes` updated                                                                                   |
| Single: cancelled                                              | `lessons.status = 'cancelled'`                                                                                                    |
| Single: back to confirmed                                      | `status = 'scheduled'`                                                                                                            |
| Instance moved/resized                                         | exception upsert `moved` with `starts_at`, `duration_minutes`                                                                     |
| Instance cancelled                                             | exception `cancelled`                                                                                                             |
| Instance back at natural place                                 | exception `restored`                                                                                                              |
| Master `UNTIL` shortened                                       | `ends_on` via `endSeriesAt` (marked tail preserved as `lessons`)                                                                  |
| Master `UNTIL` extended/removed                                | `ends_on` updated                                                                                                                 |
| Master weekday/time/duration/zone changed, still representable | inbound cut via `cutSeries` from the first unmarked future occurrence; new `lesson_series` row; mapping updated to the new series |
| Master not representable any more                              | series ends at the last past occurrence; future instances become plain events (no suggestion)                                     |
| New master carrying our markers (Google UI split)              | inbound cut, new mapping for the new master id (A2)                                                                               |
| Master or single deleted                                       | as cancelled / `ends_on` at last past occurrence                                                                                  |

Skip any entity with an unresolved command (the command's apply is authoritative for its own result; the next pass reconciles). Every inbound apply bumps `revision` only through the projection diff.

Known gap: after a Google "all events" time edit, past instances keep the master id but get new `originalStartTime` values; past marked lessons then show at Google's new time while the local mark stays on the old ref. Accounting is unaffected; display of those past blocks may lose the mark badge. Live check on the test account required [ASSUMED: A3].

`historyEligibility` must move to the projection in the same plan as the read switch, otherwise marking breaks: it reads `google_read_windows`, `google_read_events`, `google_next_lessons` today [VERIFIED: apps/api/src/calendar/history.ts:69-131,157-213]. New rule: an unmarked occurrence is eligible when it has no unresolved command and its bound projection row (kept by cleanup, Pattern 2) is not cancelled and matches the local start and duration; lessons created before `historyCutoverAt` stay eligible as today.

- Running sync or watch under `withAccessToken` (state flips on 403, R-08).
- Expanding RRULE locally.
- Creating lesson rows from inbound data without Assign or a mapping.

## Common Pitfalls

### Pitfall 1: "fresh" no longer means "read from Google now"

**What goes wrong:** `googleScheduleWindow` refines `write.ready ⇒ read.state === 'fresh' && connected` [VERIFIED: contracts/calendar.ts:194-196]; with SQL reads every write stays blocked if "fresh" keeps its old meaning.
**How to avoid:** define `fresh` = sync healthy (`last_incremental_at` within 2 poll periods, no `issue`, connection connected) and the window inside the sync window. `last_known` when the sync is failing. `observation.ts` `google_public_week_read` evidence assumes a provider round-trip per request [VERIFIED: observation.ts:135-144,260-285]; redefine or drop it.
**Warning signs:** week shows Read-only right after a quiet period.

### Pitfall 2: Command ack and sync page race

**What goes wrong:** a sync page fetched before an applied command overwrites the newer row.
**How to avoid:** upsert only when the incoming `updated` is greater than or equal to the stored one, or etag differs and `updated` is newer; command apply writes the projection row from the Google response.

### Pitfall 3: 410 handled as an error

**What goes wrong:** the token stays, every pass fails, writes blocked forever (R-11 on integrate).
**How to avoid:** 410 on any page → token null, epoch + 1, immediate full pass; never store an error that blocks writes for good.

### Pitfall 4: Webhook mounted behind auth

**What goes wrong:** Google gets 403 from `sameOrigin` or 401 from `requireSession`, counts failures.
**How to avoid:** separate route before both middlewares; only channel id + token check.

### Pitfall 5: Two refreshes without the lease

**What goes wrong:** second CAS loses and flips the connection to `reconnect_required`.
**How to avoid:** single-flight in memory, CAS loss re-reads the row.

### Pitfall 6: History eligibility left on old tables

**What goes wrong:** marks for new lessons are refused (`history_only`) once reads stop writing `google_read_*`.
**How to avoid:** move `history.ts` and `cancelled-*.ts`, `transition-view.ts`, `instance-observation.ts`, `single-command.ts`, `command-plan.ts`, `today/today.ts`, `cards/card-facts.ts` consumers in the same wave as the read switch (all files that import the old tables: `schedule/rows.ts, schedule/marks.ts, schedule/single-command.ts, schedule/command-plan.ts, calendar/history.ts, calendar/transition-view.ts, calendar/cancelled-occurrences.ts, calendar/cancelled-singles.ts, calendar/instance-observation.ts, calendar/commands.ts, calendar/read-*.ts, calendar/reads.ts, today/today.ts, cards/card-facts.ts, routes/today.ts, routes/schedule.ts, routes/students.ts`) [VERIFIED: grep this session].

### Pitfall 7: Next lesson outside the window

**What goes wrong:** `NextLessonRead.result = 'none'` asserted from a bounded window.
**How to avoid:** inside the window answer from the projection; nothing found → `unknown` with text "none in the next N weeks" decided with Design dude; never assert `none` without coverage.

### Pitfall 8: Prod is the teacher's working calendar

**What goes wrong:** the first release's inbound apply rewrites real lessons.
**How to avoid:** inbound apply only for mapped events and unmarked occurrences; Assign never automatic; release notes for Server guy list the first full pass and a dry-run counter log (counts only).

## Open Questions (for the owner)

1. **Q1 Sync window.** Recommended 8 weeks back, 53 weeks ahead; older/later weeks are read live from Google and are read-only. Cleanup keeps rows of bound lessons beyond the window so lessons up to 366 days old stay markable. Need: confirm numbers, the read-only rule for out-of-window weeks and the keep-bound-rows rule.
2. **Q2 Delete series of a lesson.** Google "delete all" removes past instances too; local history stays but past unmarked lessons then cannot be confirmed for marking. Recommended: for lessons, "Delete series" = end at the last past occurrence (Google keeps the past). Plain events: Google semantics.
3. **Q3 DELETE grant on the cache table.** Recommended: `google_calendar_events` keeps DELETE for cleanup (it is a cache, not history); other new tables get DELETE/TRUNCATE revoked like R-04.
4. **Q4 Assign of a non-weekly recurring event.** Recommended: only per occurrence; whole-series Assign only when the rule is weekly with one weekday.
5. **Q5 Where push is verified.** Locally there is no public HTTPS, so only polling can be checked. Options: a tunnel on the owner's machine with the test account, or a read-only check on prod (channel registration and receipts in logs, no writes). Recommended: tunnel locally; prod only observes logs after release.
6. **Q6 Calendar switch with bound lessons.** Recommended: switching is allowed only with no unresolved commands; future lesson events stay in the old calendar (no `events.move`); the new calendar starts without bindings (Assign available).

7. **Q7 Assign writes invisible markers to Google.** Recommended: yes (`assign` journal command patching only `extendedProperties.private`), because it keeps the mapping FK and survives reconnect/410. `25.1-UI-SPEC.md` S5 currently says the binding makes no Google write; the owner picks one before planning 25.1-08.

Not blocking (decided here, tagged as discretion): poll cadence 2 min without channel / 30 min with channel, nightly at 03:00 teacher zone, repeats `Once` / `Every week` as in UI-SPEC, plain-text description, `colorId` instead of labels. UI-SPEC U1 (Assign/Ignore scope for a series member = whole series) matches Pattern 5.

## Security Domain

| ASVS category       | Applies       | Control                                                                                                                                |
| ------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| V2 Authentication   | yes (webhook) | Channel id + SHA-256 token compare (constant time); token never logged; Caddy strips `X-Goog-Channel-Token`                            |
| V3 Session          | yes           | Teacher routes keep `requireSession` + `requireRole('teacher')` + `noStore` [VERIFIED: routes/schedule.ts scheduleRoutes `routes.use`] |
| V4 Access control   | yes           | Projection and decisions queried by `account_id` + current connection; students get no calendar data                                   |
| V5 Input validation | yes           | zod contracts for every new body; Google responses parsed with zod; `description` treated as text                                      |
| V6 Cryptography     | yes           | Existing token envelope; re-seal on calendar switch; `node:crypto` only                                                                |

| Threat                                | STRIDE                 | Mitigation                                                       |
| ------------------------------------- | ---------------------- | ---------------------------------------------------------------- |
| Forged notifications to trigger syncs | Spoofing / DoS         | Token check, per-channel rate limit, sync claim coalesces (R-06) |
| Token/calendar id in access logs      | Information disclosure | Caddy log filter deletes `X-Goog-*` secrets (R-05)               |
| HTML in event description             | Tampering (XSS)        | Text-only rendering, no `innerHTML`                              |
| Personal event data at rest           | Information disclosure | D-05 minimal fields; details on demand                           |
| Stale overwrite of Google             | Tampering              | If-Match etag; 412 → Google wins                                 |
