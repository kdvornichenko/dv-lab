Purpose: SC6 on the server; the Settings field is built in 25.1-12.

  <action>
`connection.ts` `chooseCalendar(actor, chooseGoogleCalendarRequest)` under the connection lease (D-19 keeps the lease for connect/disconnect-class actions):
- refuse `connection_required` unless the current row is `connected`; refuse `precondition_failed` when `expectedGeneration` differs; refuse `command_pending` while any command is unresolved (research Q6 recommendation, consistent with D-13); the same calendar is a no-op;
- re-read the writable list (Task 1) with an access token from `accessToken` taken before the retire, and keep that token in memory for the channel stop below (it belongs to the same Google account and stays valid after the row is retired; if it is no longer usable, take one from the new row of the same account);
- refuse an id that is not in the list;
- one transaction: open the refresh token with the old row's binding and seal it for the new row (`credentialBinding` includes the connection id); set the old row `not_connected` with `retired_at`, `encrypted_refresh_token` null, `credential_mode` null and the `revoke_*` attempt columns null (`google_connections_retired_ck`, `google_connections_credentials_ck` and `google_connections_revoke_ck` all hold); insert the new current row with the chosen calendar id, label and time zone and the next generation; `retireSyncRow` (25.1-06, `sync-store.ts`) clears the old sync row's channel and retiring columns and returns the pairs; `ensureSyncRow` inserts the new row's sync state due at once. `calendar_id` is part of every FK tuple, so retire + insert is the only path (research Pattern 9). Claims, `ensureSyncRows` and the webhook already ignore connections that are retired or not current (25.1-06); `sync-store.ts` changes here only if one of its queries misses that join.
- do not retire the previous row's mappings: items bound to the previous calendar stay untouched and are hidden because reads use the current connection only (D-13);
- after commit: `watch.stop(pairs, token)` with the returned pairs and the token taken before the retire (best effort, failures logged as counts; a channel Google keeps posting to is unknown to the webhook and gets 404) and `sync.wake` for the new connection.
Reconnect (`install` after consent): when the current row's calendar is not the primary and is still writable, keep it; remove the rule that rejects a non-primary target only for this case; a brand-new connection still uses the primary (D-04 default).

`connection-control.ts`: before revoking access on disconnect, stop the connection's channels best-effort with the still-valid token. `routes/google.ts`: `POST /calendar` → `chooseCalendar`, returns the connection snapshot. `server.ts`: pass `watch` and the sync wake into connection and connection control.
</action>
