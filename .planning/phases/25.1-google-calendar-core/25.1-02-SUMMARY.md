# Phase 25.1 Plan 02: Разделение аренды и настраиваемый OAuth callback Summary

Чтение недели, проверка пересечений и приём команд получают токен Google через `accessToken()` без advisory-аренды аккаунта: одно обновление на всех параллельных вызывающих, потеря CAS не отключает аккаунт, состояние меняет только отказ эндпоинта токена. Callback OAuth настраивается для локального клиента и туннеля.

## Что сделано

- `google-access.ts`: `accessToken(accountId, signal)` читает текущую строку `google_connections` через `deps.db`, отказывает так же, как обёртка с арендой (`connection_required`, `reconnect_required`, `permission_required`), берёт токен из кэша или из общего обновления. В deps добавлен `db: Database`, `server.ts` его передаёт. Тип результата `CalendarAccess` совпадает по форме с `CommandAccess`.
- Обновление токена: `refresh()` вызывает `gateway.refresh`; при `reconnect_required` или `permission_required` от него строка переводится в это состояние (`markRejected`), затем ошибка пробрасывается. `recordFailure` удалён: ошибка операции внутри `withAccessToken` состояние не меняет, только превращается в `CalendarFault` (не-`CalendarFault` → `provider_unavailable`, как раньше).
- Потеря CAS в `persistRefresh`: строка перечитывается; если она подключена и generation тот же, используется полученный токен и перечитанная строка; если generation сменился, один повторный refresh по новой строке; вторая потеря — `provider_unavailable`. Состояние строки при потере CAS не меняется.
- `refreshRejectedAccess` (401 при отправке) принимает строку с более новым `credential_generation` и тогда берёт кэш, а не обязательный refresh.
- `reads.ts` `refreshCalendarRead`, `schedule/calendar-conflicts.ts` `checkCalendarConflicts`, `calendar/commands.ts` `submitCalendarCommand` вызывают `accessToken`. В `commands.ts` общая транзакция `persistAdmission` для create и изменений: `SELECT ... FOR UPDATE` текущей строки подключения, повтор `requestId`, проверка id, state, generation, calendarId, затем `unresolvedCommands` и `prepareScheduleCommand`. Семантика `not_applied` по сроку и бюджету сохранена.
- `withAccessToken` вызывается только в `calendar/worker.ts` (две точки); `connection.ts` и `connection-control.ts` держат `lease.run`.
- `config.ts`: `loadCalendarConfig(env, base)` получает `NODE_ENV` и `APP_ORIGIN` из разобранной базовой конфигурации. Адрес должен быть ровно `<origin>/api/google/callback` (без query, hash, учётных данных); в production равен `APP_ORIGIN` + путь и `APP_ORIGIN` по HTTPS; вне production `https://` любой origin либо `http://localhost` / `http://127.0.0.1`. Нарушение даёт прежнюю ошибку `Invalid Google Calendar configuration` без значения. Литерала production-адреса в коде нет.
- `scripts/dev-checks/README.md`: раздел «Local Google OAuth client» (имена переменных, значения callback для локального стека и туннеля, только тестовый аккаунт владельца) и строки о двух новых скриптах.
- `deploy/RUNBOOK.md`: `## 13. Google Calendar`, `### 13.1. Stuck calendar requests` — счётчики незавершённых запросов по состояниям одним читающим SQL, `Resume recovery` в Settings > Google Calendar > Sync для `recovery_required` и `partial_recovery`, строки руками не удаляются и не правятся, при незавершённом запросе новые изменения отклоняются.

## Важно следующим планам и выкатке

- Выкатка: api в production теперь не стартует, если `GOOGLE_REDIRECT_URI` не равен `APP_ORIGIN` + `/api/google/callback` или `APP_ORIGIN` не HTTPS (ошибка `Invalid Google Calendar configuration`). `APP_ORIGIN` в `deploy/compose.yaml` совпадает с origin прежнего callback, Server guy при релизе сверяет переменную в env api.
- `dispatch.ts` `prepareDispatch` и `transition-journal.ts` `cutCompletionIsCurrent` сравнивают `credential_generation` с токеном воркера. Теперь обновлять токен может чтение без аренды: если refresh попадёт между получением токена воркером и транзакцией отправки, команда получит `not_applied`. Окно узкое (кэш обновляется только за 60 с до истечения), но цикл синхронизации 25.1-06 добавит ещё одного обновляющего; это стоит учесть там.
- Временно до 25.1-03: два параллельных чтения публикуют снимок через CAS `snapshot_revision` под `FOR UPDATE`, проигравший получает `external_change` (молча, как `provider_unavailable` в `reads.ts`). Создание урока сверяет `expectedVersion` с `snapshot_revision` и при чтении в соседней вкладке получит `precondition_failed`, как и раньше.
- 403 от Google внутри чтения теперь записывается только в результат чтения (`recordRead`), подключение остаётся `connected` (R-08).
- `CalendarAccess` экспортирован из `google-access.ts`; новые потребители (sync 25.1-06) берут `credentials.accessToken`, не `withAccessToken`.
