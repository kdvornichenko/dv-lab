`event-commands.ts` — admission and plan for plain events (research Pattern 6 and 7), from SQL only: the target row by `eventKey` (`rowByKey`), the series facts from the master row (`masterRow`), the precondition `expectedVersion === eventVersion(row)`; no Google call and no lease at admission (D-19). Rules:
- refuse with `read_only_event` when `event_type` is not `default`; with `outside_sync_window` outside the window; with `command_pending` while any command is unresolved (Phase 24 rule, kept).
- `event_create`: one-off or weekly (`RRULE:FREQ=WEEKLY;BYDAY=<weekday>` built with the existing `masterRepresentation` shape in `recurring.ts`), in the teacher default zone, with summary, `colorId`, `description`, `location` and private markers `dvKind = 'event'` plus a generated local id (D-07: app-created events map back by stored id); a deterministic event id as the existing lesson create does; no lesson rows and no `google_event_mappings` row (mappings stay lesson-only). Only timed events are created (all-day creation is not in v53).
- `event_update`: scope `one` → patch the single or the instance with `If-Match` = row etag; scope `all` → patch the master with `If-Match` = master etag (Google shifts every instance, the plain-event semantics of Pattern 7); scope `following` → trim the master `UNTIL` to the day before this occurrence and insert a new master from this occurrence with the changed fields (existing stage kinds `trim` and `create_master`). `repeats` changes: a one-off to `weekly` adds the weekly rule (scope `one`); a series to `once` with scope `all` removes the recurrence, with scope `following` trims and inserts a one-off; scope `one` cannot change repeat. A non-weekly master (D-16) allows only scope `one` with time-only changes; all-day rows allow no update (D-15). Only changed fields are sent (patch keeps the rest).
- `event_delete`: `one` → patch `status: cancelled` on the single or instance; `following` → trim `UNTIL` to the day before; `all` → master `status: cancelled`. All-day rows: `one` only (D-15).
- `GET` details builder: `calendarEventDetails` from the projection row and its master row: `repeat` (`once`, `weekly` with weekday, `other` with frequency and interval), `scopes.edit` / `scopes.delete` by the rules above, `reason` = the issue code when an option is unavailable (ScopeDialog shows one reason line).

`commands.ts`: route the three operations to `event-commands.ts` inside the existing persist transaction (connection row `FOR UPDATE`, unresolved check, `persistCommand`, wake). `dispatch.ts`: owned payload fields `colorId`, `description`, `location` are sent when present; for the three event operations the confirmed apply skips schedule rows and only records the projection facts and `advanceCommandRevision`. `command-result.ts`: the insert body and owned-field verification include the new fields; markers accept `event`.

`routes/google.ts` (session + teacher guards, zod contracts): `POST /events` (create, 202 + receipt), `POST /events/:eventKey` (update, 202), `POST /events/:eventKey/delete` (202), `GET /events/:eventKey` (details from SQL, 404 when the key is unknown, `removed` state as 404 is what the web treats as "no longer exists"). Refusals map through the existing `refusal` helper.
