`sync-store.ts` owns the sync-state rows (the other writers are `upsertEventFacts` for `revision` and `advanceCommandRevision` for `requested_seq`, both 25.1-04; the webhook bumps through `requestPass` here). Every function that selects or claims sync rows joins `google_connections` and keeps only the current connection of the account that is `connected` and has `retired_at` null (a retired row of 25.1-11 is never synced or claimed again):

- `syncWindow(now, zone)` = `[Monday(now) - 8 weeks, Monday(now) + 53 weeks)` in the teacher default zone (D-19), the only copy of the formula; `ensureSyncRow(executor, connection, now)` inserts the due row of one connection (25.1-11 reuses it inside its switch transaction) and `ensureSyncRows(db, now)` calls it for each current connected connection without a row;
- `retireSyncRow(executor, connectionId)` (used by 25.1-11 in the switch transaction): returns the channel and retiring pairs, then sets the four `channel_*` and the two `retiring_*` columns null and releases the claim (the join above keeps the row from being claimed again);
- `requestPass(executor, channelId)`: `requested_seq + 1` on the row of a current connected connection whose `channel_id` or `retiring_channel_id` matches; returns the connection id or null;
- `claim(db, connectionId | null, now)`: one `UPDATE ... SET claimed_until = now() + interval '2 minutes' ... WHERE (claimed_until IS NULL OR claimed_until < now()) AND due AND <current connected connection> RETURNING *`, due = `requested_seq > processed_seq OR next_poll_at <= now() OR next_full_at <= now()` (D-02 one task per connection, restart-safe);
- `startFull(db, claim, { tokenGone })`: `epoch + 1`, `full_started_at = now()`, and for a `410` also `sync_token = null` (Pitfall 3); every full pass starts here, so `epoch` identifies the full pass;
- `applyPass(db, claim, pass)`: one transaction; CAS on connection still current and `connected`, same `generation`, same `calendar_id`, same `epoch` as after `startFull` (or as at claim for an incremental pass), same starting `sync_token`; otherwise discard. Rows go through `upsertEventFacts` (25.1-04) with `seenEpoch` = the pass epoch, so every returned row is stamped, changed or not; only facts intersecting the window are stored. Full pass: in the same transaction delete rows of the connection with `seen_epoch` below the pass epoch inside the window and rows outside the new window, except rows matched by `boundRowCondition` (25.1-04: mapping by event id, series mapping by recurring master, our lesson marker; D-19 keeps them up to 366 days), and return the bound rows inside the window that were not stamped (Task 4 reads them from Google). Incremental pass: a fact whose times now lie outside the window deletes the stored row unless it is bound. `revision` rises at most once per pass (SC7): `upsertEventFacts` raises it when it inserted or changed a row; when only deletions happened, `applyPass` raises it by one. Save `nextSyncToken`, `processed_seq` = the `requested_seq` seen at claim, timestamps, clear `issue`, `failure_count = 0`, `full_started_at = null`, release the claim; return counts (upserted, removed, skipped, truncated);
- `recordFailure(db, claim, issue)`: `issue`, `failure_count + 1`, backoff `next_poll_at`, claim released; never touches `google_connections.state` (R-08).

`scripts/dev-checks/calendar-sync.mjs` (dvlab_test, a synthetic `SyncSource` whose pages are Google-shaped raw items passed through `parseSyncPage`, so parsing runs for real; no network), section `pass`: full pass stores the synthetic items and raises revision by 1; an empty incremental leaves revision unchanged; a changed etag raises it; a cancelled item updates status and keeps the stored times; a cancelled instance without times that was never stored is stored with `starts_at` from its original start and `ends_at` null; a zero-length item is skipped and counted while the rest of the page is stored; a 9000-character description is stored cut to 8192 and counted; an item outside the window is not stored; a second full pass that no longer returns an unbound row deletes it although nothing else changed (Google hard delete), and stamps every unchanged row with the new epoch without raising revision for the stamps; an incremental fact moved outside the window deletes the unbound row; a `410` on page 2 gives token null, epoch + 1 and a full pass whose cleanup removes unseen unbound rows and keeps the bound single, every instance row of the bound series and a marker-only row created with `calendar-commands.mjs fixtures test`, including instances older than 8 weeks; the `lessons` and `lesson_series` row counts are equal before and after the 410 (no duplicates, SC1); a master row gets `weekly` or `other` and its `recurrence_until`. Section `claim`: two concurrent claims → exactly one row; a claim whose `claimed_until` lies in the past is taken over; a sync row whose connection has `retired_at` set is never claimed and `requestPass` for its channel returns null.
