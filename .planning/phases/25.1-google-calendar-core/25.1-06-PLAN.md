`gateway-sync.ts`: `calendarSyncMethods(client, read)` composed into the gateway like `gateway-reads.ts`, all calls with `{ retry: false }`:
- `syncPage(token, calendarId, { syncToken } | { timeMin, timeMax }, pageToken, signal)`: `events.list` with `singleEvents: true`, `showDeleted: true`, `maxResults: 2500` and fields `nextPageToken,nextSyncToken,timeZone,items(id,etag,updated,status,summary,description,location,start,end,colorId,transparency,eventType,recurringEventId,originalStartTime,extendedProperties/private)`. No start-time ordering parameter (not allowed with a sync token; research Pattern 2), and do not reuse the existing ordered traversal helper. A 410 response surfaces as a dedicated error `SyncTokenGone`.
- `master(token, calendarId, eventId, signal)` (`events.get`, same field list plus `recurrence`), `colors(token, signal)` (`colors.get`, event palette), `calendarColor(token, calendarId, signal)` (`calendarList.get`, `backgroundColor`), `watch(...)` and `stopChannel(...)` (`events.watch`, `channels.stop`).

`sync-provider.ts`: `SyncSource` interface (`page`, `master`, `palette`, `calendarColor`) and `googleSyncSource(gateway, credentials)` that gets the token with `accessToken` (no lease, D-19). `normalize(item, calendarTimeZone)` maps an item to a projection fact with only the D-05 fields: all-day bounds via `startOfZonedDay`; `marker_local_id`/`marker_kind` from `extendedProperties.private` (`dvLocalId`, `dvKind`); a cancelled item may carry only id and status; an item that fails (zero length, start after end, unknown shape) is skipped and counted, never fatal (research "Bad items"). `masterFact` maps a master: `recurrence_kind` `weekly` when `recurrenceFields` from `recurring.ts` accepts the rule (one RRULE, weekly, INTERVAL 1, one weekday), otherwise `other` with `frequency` and `interval` read from FREQ/INTERVAL (D-16).

`sync-store.ts` (the only writer of `google_sync_state` besides the webhook bump and `advanceCommandRevision`):

- `ensureSyncRows(db, now)`: inserts a row for each current connected connection without one, due at once, window `[Monday(now) - 8 weeks, Monday(now) + 53 weeks)` in the teacher default zone (D-19);
- `claim(db, connectionId | null, now)`: one `UPDATE ... SET claimed_until = now() + interval '2 minutes' ... WHERE (claimed_until IS NULL OR claimed_until < now()) AND due RETURNING *`, due = `requested_seq > processed_seq OR next_poll_at <= now() OR next_full_at <= now()` (D-02 one task per connection, restart-safe);
- `applyPass(db, claim, pass)`: one transaction; CAS on connection still current and `connected`, same `generation`, same `calendar_id`, same `epoch`, same starting `sync_token`; otherwise discard. Upsert rows whose fields differ (`etag`, status, times, summary, description, location, colour, transparency, event type, recurring id, original start, markers), ignoring an incoming fact with older `google_updated_at` (Pitfall 2); store only rows intersecting the window; on a full pass delete rows with an older `seen_epoch` inside the window and rows outside the new window, never a row that has an active mapping (bound lessons stay, D-19); raise `revision` by one only if something was inserted, changed or deleted (SC7); save `nextSyncToken`, `processed_seq` = the `requested_seq` seen at claim, timestamps, clear `issue`, `failure_count = 0`, `full_started_at = null`, release the claim;
- `resetForFull(db, claim)` for `410`: `sync_token = null`, `epoch + 1`, `full_started_at = now()`;
- `recordFailure(db, claim, issue)`: `issue`, `failure_count + 1`, backoff `next_poll_at`, claim released; never touches `google_connections.state` (R-08).

`scripts/dev-checks/calendar-sync.mjs` (dvlab_test, synthetic `SyncSource`, no network), section `pass`: full pass stores the synthetic items and raises revision by 1; an empty incremental leaves revision unchanged; a changed etag raises it; a cancelled item updates status; a zero-length item is skipped and counted; an item outside the window is not stored; a `410` on page 2 gives token null, epoch + 1 and a full pass whose cleanup removes unseen unbound rows and keeps a bound row created with `calendar-commands.mjs fixtures test`; the `lessons` and `lesson_series` row counts are equal before and after the 410 (no duplicates, SC1); a master row gets `weekly` or `other`. Section `claim`: two concurrent claims → exactly one row; a claim whose `claimed_until` lies in the past is taken over.

`watch.ts`: `createCalendarWatch({ db, source, appOrigin, logger })` with `maintain(syncRow, token)` and `stopAll(connectionId, token)`:
- the address is `APP_ORIGIN + '/api/google/notifications'` and is used only when `APP_ORIGIN` is HTTPS (push needs a valid certificate; the plain local stack polls, the owner's tunnel is HTTPS, D-20);
- register when no channel: channel id = random UUID, token = 32 random bytes base64url, `params.ttl` 604800; store `sha256` hex of the token, never the token;
- renew when the channel expires within 24 hours: register a new channel, move the old one to `retiring_*`, then stop the retiring one; a failed stop keeps `retiring_*` and sets `watch_issue = 'stop_failed'`, retried on later ticks; a failed register sets `watch_issue = 'watch_failed'`;
- watch errors never change `google_connections.state` (R-08) and never block the sync pass.

`routes/google-notifications.ts`: `googleNotificationRoutes({ db, wake })` with `POST /`: reads `X-Goog-Channel-ID`, `X-Goog-Channel-Token`, `X-Goog-Resource-State`; finds the sync row whose `channel_id` or `retiring_channel_id` equals the id; compares `sha256(token)` with the stored hash using `timingSafeEqual`; unknown channel or bad token → 404 with an empty body; state `sync` → 204 without change; otherwise `requested_seq = requested_seq + 1`, `wake(connectionId)`, 204. An in-memory limit per channel id accepts at most one bump per second (extra notifications return 204; the pending bump already covers them). No body parsing, no header logging.

`app.ts`: add an optional dependency for the notification routes and mount them at `/google/notifications` after `requestContext` and before `app.use('*', sameOrigin(...))` (Google sends no Origin; research Pitfall 4).

`deploy/caddy/Caddyfile`: in both `log` filter blocks delete `request>headers>X-Goog-Channel-Token` and `request>headers>X-Goog-Resource-Uri` (the token and the calendar id must not reach access logs). Keep everything else; the CI steps `caddy validate` and `Client address trust` must stay green. The server reload is Server guy's step at release (D-12, RUNBOOK in 25.1-12).

`scripts/dev-checks/calendar-push.mjs` (dvlab_test, port 4106, api through `startCalendarApi`): seeds a sync row with a known channel id and token hash; checks without cookie and without Origin: unknown channel → 404 and `requested_seq` unchanged; wrong token → 404 unchanged; right token with state `exists` → 204 and `requested_seq` + 1; state `sync` → 204 unchanged; 20 rapid valid posts raise `requested_seq` by at most 3. Then `maintain` with an injected stub source (no network): with an `http://` origin no register call happens; with an `https://` origin a missing channel is registered and only the hash is stored; a channel expiring in one hour is renewed with the old one moved to retiring and stopped; a failing stop keeps the retiring pair, sets `watch_issue` and leaves the connection `connected`. If a `caddy` binary is available locally run `caddy validate --config deploy/caddy/Caddyfile --adapter caddyfile`, otherwise print that CI validates it. Prints `CALENDAR_PUSH_OK`.

`sync.ts`: `createCalendarSync({ db, source, watch, logger, isStopping, now? })` returning `{ start, wake, name, close }` (a `Closable` for `lifecycle.ts`):
- `start()`: `setInterval(tick, 30_000).unref()` plus one immediate tick; `wake(connectionId)` runs that connection now; an in-process `Map<connectionId, Promise>` prevents double runs; cross-process safety is the claim (D-02).
- `tick()`: `ensureSyncRows`, then `claim` each due connection; a full pass when there is no token or `next_full_at` has passed (it sets `full_started_at`, re-anchors the window per D-19, refreshes the palette with `colors.get` and the calendar colour); otherwise an incremental pass with the token; `SyncTokenGone` → `resetForFull` and an immediate full pass (Pitfall 3); master facts fetched for recurring ids touched by the pass whose master row is missing or whose instances changed (at most 50 per pass, the rest next pass).
- schedule: `next_poll_at` = now + 30 minutes with an active channel, + 2 minutes without; `next_full_at` = the next 03:00 in the teacher default zone (nightly reconcile, GCAL-05).
- after each pass `watch.maintain` for the connection.
- logs counts only (pass kind, upserted, removed, skipped, duration); never titles, places or ids (personal data, public repository).
- no lease anywhere in the loop; access tokens through `accessToken` (D-19).

`server.ts`: build the sync after credentials and gateway, pass `sync.wake` to the worker and to the notification routes, start it after `worker.start()`, add it to the managed resources. `worker.ts`: optional `afterApply(connectionId)` dependency called once a command reaches `applied`.
