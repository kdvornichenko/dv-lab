Inbound apply works from state stored in the database, never from "rows changed in this pass" (a crash between the projection commit and the inbound step, a lock conflict or a pending command would otherwise leave a lesson diverged from Google for good):

- `sync-store.ts`: `inboundWork(executor, connectionId, after, limit)` returns the rows matched by `boundRowCondition` (25.1-04) whose `etag` differs from `inbound_applied_etag` (null included), grouped by local entity (a single lesson; an occurrence by series and original date; a series by its master), in a stable entity order after the cursor `after`, at most 200 rows per page (frozen rows stay in the list, so paging by cursor keeps them from hiding later rows); `markInboundApplied(executor, connectionId, rows)` sets `inbound_applied_etag = etag` for exactly those rows when their `etag` is still the one read.
- `schedule/inbound-apply.ts` (owned by `schedule`; called from `calendar`; it never imports `cards`) — research Pattern 8, under `lockSeries` / `lockLesson`: `applyInbound(tx, item)` compares the current projection rows of one entity with the current local state and changes only the difference; it returns `applied`, `unchanged` or a skip reason. The caller (`sync.ts`) opens one transaction per entity, calls it, and on `applied` or `unchanged` calls `markInboundApplied` in the same transaction. Skips leave the rows unstamped, so the next run reconciles them:
  - `skipped_pending`: the entity has an unresolved command (the command's own apply decides; the worker's `afterApply` wakes a pass, 25.1-06, so the entity is reconciled right after the command applies);
  - `skipped_locked`: the row lock is not obtained at once (`NOWAIT` or `SKIP LOCKED`);
  - `skipped_past` (D-21): a single lesson or an occurrence whose start is not after now is frozen like a marked one (`canChange` false): Google's move or cancel of it is not applied, nothing is written, and the count is logged. Marks live on the lesson or occurrence (series id and original date), never on the Google event.
  - `skipped_marked`: a single lesson with a `lesson_marks` row for its `lesson_id`, or an occurrence with a mark for its `series_id` and `original_on`, is frozen (D-08): neither its time nor its status changes; if the mark is removed later, the next run applies Google's state.
- Comparison rules (state, not deltas):
  - single: projection start/end differ from `starts_at` / `duration_minutes` → set them (reuse `applyLessonChange` of `changes.ts`, which takes `durationMinutes` since 25.1-07); row `cancelled` and lesson scheduled → status `cancelled`; row confirmed and lesson cancelled → `scheduled`;
  - instance (including a time-less cancelled tombstone found by `recurring_event_id` + `original_start`): Google start/duration differ from the occurrence → `moved` exception with start and duration; row cancelled → `cancelled` exception; Google back at the natural time with the series duration while an exception exists → `restored` (GCAL-08: one occurrence moves only that occurrence);
  - master: `recurrence_until` earlier than the local `ends_on` → `endSeriesAt` (marked tail preserved); later or null → `ends_on` updated; weekday/time/duration/zone different and still weekly → cut with `cutSeries` from the first unmarked future occurrence into a new `lesson_series` row and move the mapping to it (rule columns immutable, D-10); no longer weekly → end the series at the last past occurrence, future instances become plain events without suggestion; a new master carrying our marker for an existing series (Google "this and following" split, assumption A2) → cut at the split date and bind the new master to the new local series; cancelled → `ends_on` at the last past occurrence;
  - never deletes rows, never creates lessons for unbound events (D-07), never writes marks;
  - if moving a mapping to a new series hits a database constraint that the existing columns cannot satisfy, stop and report the constraint name instead of changing the schema.
- `sync.ts`: after every committed pass, including an empty incremental one, walk all pages of the inbound work of the connection; log counts only (`applied`, `unchanged`, `skipped_marked`, `skipped_pending`, `skipped_locked`). `createCalendarSync` takes an optional `hooks.afterPassCommit(connectionId)` for the check script (throwing from it simulates a crash between the projection commit and the inbound step); production passes none.
