# Phase 25.1 — Plan index

## Outcome

The schedule becomes a two-way Google Calendar for any event (ROADMAP Phase 25.1 goal): the teacher creates, moves, resizes, edits and deletes events in the app, sees Google changes without an open page, and Google wins on conflicts. Requirements GCAL-04..GCAL-08, success criteria SC1-SC7, locked decisions D-01..D-20.

12 plans, 8 waves, 36 tasks. Order follows D-01: sync rewrite (waves 1-4), editing core (waves 5-7), calendar choice (waves 7-8).

Mode: `TRACER_MODE=false`. The end-to-end paths (browser -> api -> Postgres, api -> journal -> Google) are proven by Phases 20-24; this phase replaces layers behind stable contracts. Every plan ends with an end-to-end check of its own slice (a dev-check script, a browser script, or both).

Estimates: `estimate-calibration` factor 1, 0 samples, confidence low; `raw_tokens = tokens`.

Rules held by every wave: at most one plan that edits `apps/api` and at most one web plan; no same-wave `files_modified` overlap (checked); `yarn workspace @dv-lab/api build` and `yarn build` run only in 25.1-12, and `yarn test` (it wipes dvlab_test) only there; ports 3000/4000 and dvlab_dev belong to the web plan of the wave; api plans use dvlab_test with their own 41xx port. A web plan starts the api with `scripts/dev-checks/calendar-dev-api.mjs` (no watch); if a parallel api edit is mid-way, it waits and restarts (EXECUTOR-RULES 2).

Lock split in wave 1 (requested): 25.1-02 removes the account lease from reads, the overlap check and admission at once. Reads stop calling Google in wave 2 (25.1-03) because the projection table they read is created by 25.1-01 in wave 1; both cannot compile in parallel.

Interim state inside the branch (no release mid-phase): between waves 2 and 3, lesson commands and marks of newly confirmed lessons are refused (they still look at the old snapshot tables until 25.1-04); between waves 2 and 4 nothing fills the projection except the synthetic seed.

- 25.1-09: `calendarEventView.suggestion`, the `assign` command member.

## Acceptance without Google (D-11, user rule)

- `calendar-offline.mjs` preload makes Google hosts unresolvable in every check process; `calendar-env.mjs probe` proves it.
- `calendar-seed.mjs` creates a synthetic connected calendar (connection, parked sync state that no pass can claim, projection rows with `Alex Example NNNN` / `Synthetic event NN` titles) in dvlab_test or dvlab_dev and removes it.
- API logic is checked by scripts that call module functions with stub gateways or a synthetic `SyncSource`; the worker runs in-process only with a stub gateway (`calendar-commands.mjs fixtures`).
- Browser checks intercept every write with `page.route`, assert the request body, answer with synthetic receipts, and emulate the server result through the seed (`bump`, inserted rows), so nothing is dispatched.
- SC7 is checked with `pg_locks` while another session holds the account advisory lock.

Owner live session (not a plan task; local stack, local OAuth client, test account only, D-11/D-20): push through an HTTPS tunnel, a real 410, provider assumptions A1-A7 of 25.1-RESEARCH, every scope written from the app and from Google, Assign/Ignore, calendar switch. Procedure in `scripts/dev-checks/README.md` (25.1-12). Plan 24-14 is replanned on the same session.

## Owner decisions needed

1. Per-entity command barrier (research R-35): planned as "keep the Phase 24 global rule". Say if a stuck request should block only its own event.
2. D-19 read rule applied strictly: description, place and the series rule are stored in the projection so event details never call Google. The Settings calendar list (25.1-11) is read from Google on demand (it is not a schedule read). Confirm both.
3. Old snapshot tables (`google_read_windows`, `google_read_events`, `google_next_lessons`): code stops using them; an optional one-off truncate on prod by Server guy, the drop in a later release.
4. GCAL-06 text vs D-07: update REQUIREMENTS wording to "suggested".
5. Live checks need the local OAuth client and the test account (D-11, D-20); until then A1-A7 stay assumptions.

## Risks

- 25.1-04 rewires about fifteen Phase 24 files around preconditions and history; marks and lesson commands are broken inside the branch between waves 2 and 3.
- 25.1-06 is the heaviest plan (sync + push); 25.1-09 inbound apply touches real lessons on prod after release: mapped or marked entities only, marked occurrences frozen, counts logged.
- Provider behaviour not stated in the local docs (A1-A7: incremental scope after a bounded full pass, marker copy on a Google split, `originalStartTime` after an "all events" edit, Assign on events organized by others) is proven only in the owner session.
- Moving a mapping to a new local series on an inbound cut may meet existing mapping constraints; 25.1-09 stops and reports instead of changing the schema.
- The DNS preload is the guarantee that checks never reach Google; 25.1-01 proves it before any later plan relies on it.
