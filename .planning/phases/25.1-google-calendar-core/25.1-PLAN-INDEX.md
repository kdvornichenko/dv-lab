# Phase 25.1 — Plan index

## Outcome

The schedule becomes a two-way Google Calendar for any event (ROADMAP Phase 25.1 goal): the teacher creates, moves, resizes, edits and deletes events in the app, sees Google changes without an open page, and Google wins on conflicts. Requirements GCAL-04..GCAL-08, success criteria SC1-SC7, locked decisions D-01..D-20.

12 plans, 8 waves, 41 tasks. Order follows D-01: sync rewrite (waves 1-4), editing core (waves 5-7), calendar choice (waves 7-8).

Mode: `TRACER_MODE=false`. The end-to-end paths (browser -> api -> Postgres, api -> journal -> Google) are proven by Phases 20-24; this phase replaces layers behind stable contracts. Every plan ends with an end-to-end check of its own slice (a dev-check script, a browser script, or both).

Estimates: `estimate-calibration` factor 1, 0 samples, confidence low; `raw_tokens = tokens`.

## Acceptance without Google (D-11, user rule)

- `calendar-offline.mjs` preload makes Google hosts unresolvable in every check process; `calendar-env.mjs probe` proves it.
- `calendar-seed.mjs` creates a synthetic connected calendar (connection, parked sync state that no pass can claim, projection rows with `Alex Example NNNN` / `Synthetic event NN` titles) in dvlab_test or dvlab_dev and removes it.
- API logic is checked by scripts that call module functions with stub gateways or a synthetic `SyncSource`; the worker runs in-process only with a stub gateway (`calendar-commands.mjs fixtures`).
- Browser checks intercept every write with `page.route`, assert the request body, answer with synthetic receipts, and emulate the server result through the seed (`bump`, inserted rows), so nothing is dispatched.
- SC7 is checked with `pg_locks` while another session holds the account advisory lock.

Owner live session (not a plan task; local stack, local OAuth client, test account only, D-11/D-20): push through an HTTPS tunnel, a real 410, provider assumptions A1-A7 of 25.1-RESEARCH, every scope written from the app and from Google, Assign/Ignore, calendar switch. Procedure in `scripts/dev-checks/README.md` (25.1-12). Plan 24-14 is replanned on the same session. The session's confirmation of A2, A3 and A6 is a release condition (RUNBOOK 13.2, 25.1-12): the first full pass on prod reconciles every bound lesson with Google. No report-only mode is built.

## Risks

- 25.1-04 rewires about twenty-one Phase 24 files around preconditions, history, dispatch and the confirmed apply; marks and lesson commands are broken inside the branch between waves 2 and 3. Its task order keeps the typecheck green (dispatch and overlaps leave the window helper before admission deletes it).
- 25.1-07 is the largest plan (21 files): event commands only reach `applied` if the dispatch and verification changes of its Task 2 hold; its acceptance dispatches every operation through a stub gateway with the real `verifyGoogleResult`.
- 25.1-06 is the heaviest sync plan (sync + push); 25.1-09 inbound apply touches real lessons on prod after release: mapped or marked entities only, marked singles and occurrences frozen, work list by state, counts logged; the first full pass reconciles every bound lesson, so the release waits for the owner session (A2, A3, A6).
- Event scope `following` reuses the cut stages; if the cut verification compares fingerprints of a `create_master` that owns colour, description or place, 25.1-07 stops and reports instead of widening.
- Provider behaviour not stated in the local docs (A1-A7: incremental scope after a bounded full pass, marker copy on a Google split, `originalStartTime` after an "all events" edit, Assign on events organized by others) is proven only in the owner session.
- Moving a mapping to a new local series on an inbound cut may meet existing mapping constraints; 25.1-09 stops and reports instead of changing the schema.
- The DNS preload is the guarantee that checks never reach Google; 25.1-01 proves it before any later plan relies on it.
