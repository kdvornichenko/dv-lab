# Phase 25.1 Plan 11: выбор календаря внутри подключённого аккаунта (сервер) Summary

**`GET /google/calendars` отдаёт календари подключённого аккаунта, доступные для записи, с отметками основного и текущего; `POST /google/calendar` под арендой подключения в одной транзакции отставляет текущую строку, создаёт новую для выбранного календаря с перезапечатанным refresh token и готовой к полному проходу строкой синхронизации, очищает каналы прежней строки и после коммита останавливает их токеном, взятым до отставки. Уроки и события прежнего календаря не трогаются и скрыты из сетки (D-13); повторное подключение сохраняет выбранный календарь (D-04).**

## Что сделано

- **Шлюз.** `calendars(token, signal)` в `gateway-sync.ts`: `calendarList.list` с `showHidden: true`, `maxResults: 250`, полями id, summary, summaryOverride, timeZone, primary, deleted, accessRole, backgroundColor; не больше 40 страниц, повтор токена страницы или превышение — `invalid_provider_data`. Схема записи своя (импорт `calendarEntry` из `gateway.ts` дал бы цикл, как в 25.1-06).
- **Список.** `connection.listCalendars(actor)`: токен из `credentials.accessToken` без аренды с бюджетом 30 с, `current` — совпадение с календарём строки, из которой выдан токен. Маршрут разбирает ответ `googleCalendarList`; отказ через `refusal` (409 при отсутствии подключения).
- **Смена (`chooseCalendar`).** Под `lease.run`: текущая строка должна быть `connected` (`connection_required`), поколение — равно `expectedGeneration` (`precondition_failed`), тот же календарь — no-op, незавершённая команда аккаунта — `command_pending`. Затем `accessToken` (токен остаётся в памяти) и свежий список; id не из списка — `invalid_request` 400. Транзакция: `requireConsentSession`, `SELECT ... FOR UPDATE` текущей строки и повтор всех проверок по заблокированной строке; refresh token открывается привязкой этой строки и запечатывается для новой (`credentialBinding` с новым id, `credential_generation + 1`); старая строка — `not_connected`, `issue = connection_required`, `retired_at`, токен, `credential_mode` и `revoke_*` null (CAS по id, поколению, `credential_generation`, `connected`); новая строка — `connected` с id, меткой и зоной выбранного календаря, поколение +1, `historyCutoverAt = now()`, прежний `snapshot_revision`; `retireSyncRow` возвращает пары канала и очищает колонки, `ensureSyncRow` вставляет строку новой строки с `next_poll_at` и `next_full_at` = now. `google_event_mappings` в этом пути не меняется. - **Повторное подключение.** `completeConsent` после `primary()` вызывает `consentTarget`: если у строки календарь не основной, читается список; календарь есть — строка обновляется на месте с ним (`switching` ложно), нет — прежнее правило с `wrong_primary`. Строка без календаря получает основной.
- **Отключение.** `disconnect` берёт токен из `accessToken` (null, если строка не `connected`), останавливает каналы `watch.stopAll` до транзакции, в транзакции перехода вызывает `retireSyncRow`. Остановка стоит до транзакции, потому что насос с интервалом 1 с начинает `revoke` сразу после перехода в `disconnecting`, а отзыв гранта делает токен недействительным.
- **server.ts.** Порядок: `credentials` → `watch` → `sync` → `connection` (`watch`, `wake`) → `control` (`watch`) → `worker` (`afterApply: wake`) → `commands`.
- **sync-store.ts** не менялся: все захваты, `requestPass`, `notificationTarget` и `ensureSyncRows` уже соединяют текущее подключение `connected` без `retired_at`.

## Отклонения от плана

### Исправлено по ходу

**1. [Правило 3] `connection.ts` в коммите задачи 1.** У маршрутов нет `credentials` и `gateway`, поэтому чтение списка — метод `listCalendars` сервиса подключения; маршрут только разбирает ответ.

**2. Порядок проверок `chooseCalendar`.** Состояние, поколение, тот же календарь (no-op), незавершённые команды, список. Проверки идут до сетевого вызова и повторяются по строке под `FOR UPDATE`: обновление токена между ними может поднять `credential_generation`, а конверт открывается привязкой заблокированной строки.

**3. Запасной токен «из новой строки» не реализован.** Токен из `accessToken` действует не меньше 60 с (`cached`), смена календаря грант не отзывает, остановка идёт сразу после коммита; офлайн такой сбой не воспроизвести. Сбои остановки только считаются в журнал, канал, который Google продолжит слать, получит 404.

**4. [Правило 2] Отключение очищает колонки канала.** Без очистки повторное подключение на той же строке получило бы от `maintain` ответ `kept` для канала, которого у Google уже нет, и push молча пропал бы до срока канала. Каналы останавливаются до транзакции перехода (см. «Что сделано»); канал, зарегистрированный между остановкой и транзакцией, очищается, но не останавливается.

**5. Правило повторного подключения для всех состояний.** Строка `not_connected` (подключение после отключения), чей не основной календарь доступен для записи согласившемуся аккаунту, сохраняет его. Крайний случай: при смене аккаунта, если прежний календарь расшарен новому с правом записи, он сохраняется. Ветка `retire()` в `install` (смена аккаунта) по-прежнему отставляет сопоставления — поведение до D-13, план его не меняет.

**6. `issue = connection_required` на отставленной строке и `historyCutoverAt = now()` на новой**, как в ветке смены `install`. Следствие: уроки прежнего календаря, начавшиеся до смены, остаются доступными для отметки по правилу cutover; начинающиеся после смены не видны в сетке и не подтверждаются проекцией (D-13); существующие отметки не меняются (проверено 1 → 1).

**7. Проверки сверх плана:** календарь не из списка, тот же календарь, отказ повторного подключения при недоступном календаре (`wrong_primary`), раздел 7 (отключение).
