Ревью планов фазы 25.1 Google Calendar Core

Зачем · цель фазы и решения D-01–D-20 The schedule becomes a two-way Google Calendar for any event, not only lessons. The teacher creates, moves, resizes, edits and deletes events in the app and sees changes made in Google without an open page. Google wins when both sides changed. Lessons stay the app's own model; every other event is a plain calendar event. the sync rewrite comes first, then the editing core, then the calendar choice; chat follows after this phase. one background task per connection with no shared account-wide lock, the week version grows only on real changes, a bounded sync window, cleanup of stale rows, no tables beyond what the model needs. Push notifications trigger incremental sync with `syncToken`; a real `410` triggers a full resync with no duplicate lessons; channels are renewed before expiry; a nightly reconcile recovers missed delivery. create any event; move and resize with the mouse; delete one occurrence, a whole series, or this and following; repeats; colors; description and place. Views: week only. the account can pick a calendar inside the connected Google account (PRIMARY stays the default). keep only the Google fields the app needs; no raw event copies. events that are not lessons are shown as events with title, time and Google color; they can be created, moved, resized and deleted like any other event. an event whose title matches a student name is only suggested; the teacher binds it with Assign or discards it with Ignore. Nothing is bound automatically. App-created events map back to their lessons by stored id first. when the same item changed in both places the Google version remains after sync. Marks and accounting history of past lessons are never rewritten by inbound edits. no upper limit (the 15-240 CHECK was removed in PR 32). The schedule day runs 02:00-02:00 (PR 25). rows change status, `kind` or `ends_on`. Series rule columns stay immutable after insert; a cut gives a new series live Google checks only locally on the owner test account with a local OAuth client; prod holds the teacher's working calendar and receives releases without live testing. No new unit or e2e tests; acceptance by scripts, logs and the browser. Claude only, no Codex. Server work goes through Server guy, design through Design dude. lessons and events are bound to the calendar they were created or matched in. When the account picks another calendar, items bound to the previous one stay untouched on the app side and are hidden from the grid. two scopes, this occurrence and this and following (the existing cut and End series); no "all" for lessons, past history is never rewritten. Plain events get this, this and following, all. shown as a narrow strip above the grid; the only action is delete; no move or resize. only weekly repeats are supported; other Google repeat rules are shown read-only (a single occurrence may still be moved or deleted). apply to the whole recurring series. Ignore hides the suggestion and keeps the event as a plain event; it is not undoable in this phase, a manual Assign stays available in the event details at any time. Assign writes a private extended property with the lesson id into the Google event, so the link survives reconnection and a full resync (`410`). 8 weeks back and 53 weeks forward; weeks outside the window are read-only. Rows of bound lessons are never cleaned … Reads use only SQL over the projection, never Google and never the account lease; the lease stays for command sending and connect/disconnect. DELETE is granted only on the projection cache table a temporary tunnel to the local stack with the owner test account and a local OAuth client (the production callback is hard-coded in `apps/api/src/config.ts` and must become configurable for local runs). Prod and the working calendar are not touched.
