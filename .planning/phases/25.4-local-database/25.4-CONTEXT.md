# Phase 25.4: Local Database - Context

**Gathered:** 2026-10-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Every teacher screen except chat reads from a copy of the teacher's data in the browser (IndexedDB) and opens at once, also without a network. The server keeps one change journal per account with a growing number. On open the app asks for everything after its number, and while the app is visible an SSE stream delivers new rows. Writes stay on the server. Calendar weeks older than the sync window open from a read-only history archive on the server.

The measured reason (Server guy, 2026-10-15): the api is fast (`/schedule/week` p50 46 ms), but the VPS is in Canada (RTT from the teacher ~257 ms, TLS 0.6–1.8 s) and screens wait on chains of sequential requests.

Out of scope: chat, the write rules and their confirmation, the sync window and the rules for old lessons, offline writes, moving the VPS, bundle size work.
</domain>

<decisions>
## Implementation Decisions

### Owner decisions before the discussion (locked)
- **D-01 Writes stay on the server.** The local database is a read copy. Writes go through the api as today with the optimistic block (`OptimisticWrite`); the confirmed result comes back as a journal delta. Google confirmation, Confirm/Decline in chat and every write rule stay as they are. A Linear-style local write queue and offline writes are rejected (conflicts and rollbacks for money and the schedule).
- **D-02 Change journal and stream.** One journal per account on the server with a growing number. Every write appends a row, including the Google sync passes, the dispatcher and the import. The app asks for everything after N on open and keeps an SSE stream while it is visible. Re-reading sections by revision is rejected. — **Reversibility:** costly — a new table and a published sync contract that every writer and every screen depend on.
- **D-03 Calendar history archive.** A read-only archive on the server, filled once from Google and extended by the weeks that leave the sync window. The sync window (8 weeks back, 53 forward, D-19 of 25.1) and the rules for old lessons do not change. Reading Google on demand and widening the window are rejected. — **Reversibility:** costly — a new table and a backfill from Google.
- **D-04 Scope.** Everything except chat: schedule and events, students and cards, payments, lessons and marks, notes and vocabulary, comments, settings, Today. Chat stays server-only.
- **D-05 Sign out wipes the local database** (IndexedDB and every device key).

### What the device stores
- **D-06 The device stores screen answers, not table rows.** The api keeps the one assembly of derived reads (balance, Today, the week, card facts, read state); the browser stores the answers it gets, keyed by what was asked. A journal row names which answers a write touched, and the device re-reads only those. This settles AR-03: no second assembly in the browser. — **Reversibility:** costly — switching to rows later means moving the assembly into `packages/core` and rewriting the local store.
- **D-07 A time-dependent answer without a network is shown as it was, with its update time** (for example Today after midnight: the last answer, marked with the time it was fetched). Nothing is recomputed on the device.

### Freshness and connection
- **D-08 The SSE stream is open only while the app is visible.** On hide it closes; on return the app asks for everything after N, then reopens the stream.
- **D-09 Without a network the write buttons are off and say why.** The read status icon (in the toolbar today) carries the offline state and the time of the device data. 25.2 D-40 «PWA, no offline» is superseded for reading only; writing still needs a network. The look of the offline state is asked from Design dude.

### First load and the device database
- **D-10 After sign-in the whole account loads in the background as one stream;** each screen opens as soon as its part has arrived.
- **D-11 A new local database format wipes the database and loads it again,** without asking. No migrations on the device.
- **D-12 The app asks the browser for persistent storage silently** (`navigator.storage.persist()`), with no hint or prompt in the interface.

### Calendar history archive
- **D-13 The archive holds the whole history** of the calendar, from its first event.
- **D-14 The whole archive is re-read from Google once a week** to catch edits of past events; between re-reads archived weeks do not change.

### Architecture in the phase's area (see 25.4-ARCH-REVIEW.md)
- **D-15 (AR-01):** deepen the web sync layer as its own plan before the screens move: it replaces `notifyCache`, `announceChange`, `use-google-sync` polling, `useCalendarRefresh`, focus/visibility re-reads, `FRESH_MS` and the `/auth/me` checks around week reads; the old signals are removed in this phase.
- **D-16 (AR-02):** deepen one owner of reads in web over IndexedDB as its own plan before the screens move; every screen reads through it and every answer is parsed with its contracts schema.
- **D-17 (AR-04):** deepen one api module that appends journal rows as its own plan before the plans that write to the journal; every writer goes through it, the background ones included (`sync-store` `applyPass`/`applyReads`, `inbound-apply`, `dispatch`, `import/apply-packet`).
- **D-18 (AR-05):** deepen `calendar/sync-store.ts` so that a week leaving the sync window is an event the archive takes, as its own plan before the archive plan.

### Design (v119, component LocalData, code-sync 155)
- **D-19 Offline and first load have one carrier: the read status icon.** On Schedule it replaces the Google states while there is no network. On Today, Students, the profile, Payments and Settings the same icon sits in the top bar left of the page actions and is drawn only when offline or during the first load. Whether the top bar reserves its slot or shifts once is the owner's answer in the design session: take it from the design version after v119.
- **D-20 Writes without a network:** `aria-disabled` (not `disabled`) at 50% with `aria-describedby` to the reason; laptop tooltip «Needs a network», phone a caption line under the action group; a dialog keeps its values, Close works, the main button is off and the footer status row says «Offline. Changes need a network.»; Student actions opens with the reason as the first row; week drag and tap do nothing; navigation stays.
- **D-21 Stale answer:** one muted caption line under the Today header «Not updated since Thu 15 Oct, 21:52 (VN)», only when offline and the answer's teacher day (ends 02:00) is not the current one.
- **D-22 First load:** skeletons as now (SkeletonSwap); the status slot shows a spinner «Loading your data…» and goes away silently. Offline with a screen part never loaded: EmptyState «Not on this device yet», no action. Back online: nothing is shown, no toast.

### Claude's Discretion
- Several tabs: one tab writes the local database (leader), the others read; the mechanism is the planner's.
- Stream format, reconnect and backoff, journal retention, and what happens when a device is too far behind (a full reload is acceptable).
- The format of the first-load stream (for example NDJSON).
- How the nightly full Google pass writes only real changes to the journal.
- The order in which screens move to the local database inside the phase.
- Replacing the PR 44 device copy (`apps/web/lib/device-store.ts`, `sessionEpoch`, on branches `gsd/phone-drag` and `gsd/schedule-bundle`) once that PR is merged.

<code_context>
## Existing Code Insights

### Reusable Assets
- SSE: `apps/api/src/routes/chat.ts:241-290` (`streamSSE` with queue, wake, heartbeat with `readSession`, abort, no-store) fed by the in-process `subscribe` in `apps/api/src/chat/runs.ts:971`. There is no `pg_notify`/`LISTEN` in the api; background writers must hand events to the stream in-process the same way.
- Google range read: `apps/api/src/calendar/event-titles.ts` reads any range through `GoogleGateway` — a base for the archive backfill and the weekly re-read.
- `revision` columns on `students`, `student_sections`, `payments`, `lesson_marks`, `chat_command_prompts` (`packages/db/src/schema.ts`), and `google_sync_state.revision`.
- `apps/web/lib/api-client.ts` (`apiRequest`, `notifyCache`, `SESSION_CACHE_CHANNEL`, `DATA_CHANGED_CHANNEL`) — the one client path to the api; the new read owner sits on it.
- Contracts schemas in `packages/contracts/src/*` — the device parses stored answers with them.

### Established Patterns
- Reads are assembled in the api over `now` (`today/today.ts`, `schedule/window-blocks.ts`, `cards/card-facts.ts`, `calendar/read-model.ts`); D-06 keeps it so.
- Writes run in transactions with `FOR UPDATE`; schedule rows are never deleted (status or `ends_on` change).
- Migrations only add in one release; the journal and the archive are new tables.
- `/ws` exists (`apps/api/src/app.ts:79-89`) as an echo without product callers; the phase uses SSE and leaves `/ws` alone.

### Integration Points
- Every api writer listed in AR-04 appends through the journal module.
- `calendar/sync-store.ts` cleanup (`:339-351`, `:386-397`) becomes the hand-off to the archive.
- `calendar/read-model.ts:81-82` (`outside_sync_window`) reads from the archive for weeks older than the window.
- Sign out in `api-client.ts` wipes the local database.
- Domain tables have no `account_id`; the single active teacher is held by `accounts_one_active_teacher_uq` (`packages/db/src/schema.ts:48`).
</code_context>
