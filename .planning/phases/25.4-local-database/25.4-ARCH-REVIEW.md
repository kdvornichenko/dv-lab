## Находки

### AR-01. «Данные изменились»: пять механизмов в web, клиент угадывает смысл сервера
- Файлы:
  - `apps/web/lib/api-client.ts:115-135`: `notifyCache` по методу и белым спискам `UNCHANGED_PATHS`, `STATUS_CHECK`. Сигнал без содержимого.
  - `apps/web/app/(app)/chat/_components/use-chat.ts:317-320`: `announceChange`.
  - `apps/web/components/app/use-google-sync.ts:9-32`: опрос `/google/sync` раз в 20 с.
  - Сравнение `read.revision` с ревизией sync: `use-today.ts:45-49`, `use-schedule-week.ts:284-297`.
  - `calendar-command-provider.tsx:15-63,119`: реестр `useCalendarRefresh`.
  - Перечитывание по focus и visibilitychange в шести хуках.
  - `FRESH_MS` в `use-schedule-week.ts:20`.
  - `router.refresh()` в `app-shell.tsx:61`.
  - Двойной `/auth/me` вокруг чтения недели: `calendar-command-provider.tsx:19,21`. Без сети это чтение даёт null.
- Трение: что и когда перечитать, решает каждый вызывающий. Сервер знает, что изменилось, клиент угадывает.
- Тест удаления: без `notifyCache` каждый экран изобретёт сигнал заново. Модуль работает, но мелкий.
- Категория: ports & adapters (web → api).
- Тесты: нет.
- Связь с фазой: расширяет. Фаза заменяет всё это потоком «после N».
- Сила: Strong.
- Рекомендация: в этой фазе.

### AR-02. Чтение данных в web без владельца
- Файлы: около 52 вызовов `apiRequest('GET', …)`. Из них 33 приводят тип без проверки (например `student-profile.tsx:38`, `use-today.ts:30`, `payments-tab.tsx:30`, `lessons-tab.tsx:49`), 19 разбирают через zod `safeParse` (`overview-tab.tsx:67-80`, `calendar-command-transport.ts:84-106`). Серверный `getMe` идёт через `apps/web/lib/session.ts:8-20`.
- Трение: каждый экран сам владеет запросом, разбором и состояниями loading, error, ready. Для одного правила два режима ошибок: битый ответ после приведения типа не ловится.
- Тест удаления: модуля нет, понятие размазано по ~52 вызывающим. Фаза переводит каждый на IndexedDB.
- Категория: ports & adapters.
- Тесты: нет, есть e2e и `scripts/dev-checks/*-web.mjs`.
- Связь с фазой: расширяет.
- Сила: Strong.
- Рекомендация: в этой фазе.

### AR-03. Производные чтения собираются в api поверх `now`, не в core
- Файлы:
  - `apps/api/src/today/today.ts:44-93,95-114`;
  - `apps/api/src/schedule/window-blocks.ts:33-50`;
  - `apps/api/src/cards/lessons-range.ts:117-162`;
  - `apps/api/src/cards/card-facts.ts:17-45`;
  - `cards/ledger.ts:57-91`;
  - `apps/api/src/calendar/read-model.ts:69-89,268-322`.
- Трение: ответы сделаны под экраны. Одна оплата меняет `/students`, `/students/:id`, `/today`, `/students/:id/lessons` и `/payments`. Если браузер хранит строки, ему нужна эта сборка, то есть третья копия. Если хранит ответы, журналу нужно знать, какие ответы задевает запись и как они устаревают со временем.
- Тест удаления: модули нужные, риск — браузерная копия сборки.
- Категория: in-process.
- Тесты: прямых нет, есть `e2e/today.spec.ts` и `scripts/dev-checks/ledger-api.mjs`.
- Связь с фазой: расширяет.
- Сила: Strong.
- Рекомендация: в этой фазе, как решение для планировщика (что хранит браузер: строки или ответы).

- Тесты: `apps/api/test/calendar-projection.test.ts` — один случай, без ревизии.
- Связь с фазой: расширяет.
- Сила: Strong.
- Рекомендация: в этой фазе.

## Факты для планировщика (не находки)
- `/ws` (`apps/api/src/app.ts:79-89`, `handle /ws` в Caddyfile) — эхо без продуктовых вызывающих, шов на будущее. Фаза выбрала SSE, `/ws` не удаляется.
- Единственный живой поток к вкладке — внутрипроцессный `subscribe` чата (`chat/runs.ts:971`) → `streamSSE` (`routes/chat.ts:241-290`): очередь, wake, heartbeat с повторным `readSession`, abort, no-store. В api нет `pg_notify` и `LISTEN`.
- В доменных таблицах нет `account_id`. Единственного учителя держит `accounts_one_active_teacher_uq` (`packages/db/src/schema.ts:48`), поэтому журнал «на аккаунт» привязывает строки к аккаунту неявно.
- `apps/web/lib/device-store.ts` и `sessionEpoch` из PR 44 пока только в ветках `gsd/phone-drag` и `gsd/schedule-bundle`.
- `google_read_windows`, `google_read_events`, `google_next_lessons` никто не пишет и не читает. Их удаление уже отложено.

## Решения

Ответ владельца на странице обсуждения 2026-10-15, все рекомендации приняты.

| id | название | решение | причина | модуль-владелец |
|----|----------|---------|---------|-----------------|
| AR-01 | Сигналы «данные изменились» в web | в этой фазе | фаза заменяет их журналом и потоком «после N» | новый слой синхронизации web (заменяет `notifyCache`, `use-google-sync`, `useCalendarRefresh`) |
| AR-02 | Чтение данных в web без владельца | в этой фазе | каждый экран переходит на локальную базу | новый владелец чтения web поверх IndexedDB |
| AR-03 | Производные чтения в api поверх `now` | в этой фазе, решено как D-06 | устройство хранит ответы экранов, сборка остаётся одна в api | api: `today/today.ts`, `schedule/window-blocks.ts`, `cards/card-facts.ts`, `calendar/read-model.ts` |
| AR-04 | Одно место записи в журнал | в этой фазе | правило «каждая запись добавляет строку» для всех писателей, фоновых тоже | новый модуль журнала в api |
| AR-05 | Событие «неделя ушла из окна» | в этой фазе | архиву нужен свой момент вместо DELETE | `calendar/sync-store.ts` + новый модуль архива |

## Для планировщика
- Углубить: модуль журнала изменений api (AR-04) — отдельным планом до планов, которые пишут в журнал.

- Углубить: событие «неделя ушла из окна» в `sync-store` (AR-05) — до плана архива.
