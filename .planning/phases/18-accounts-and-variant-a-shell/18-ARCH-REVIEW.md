## Находки

### 1. Правило входа собирает вызывающий код

- Файлы (эталон ielts, не код области):
  - `/Volumes/T7/personal/ielts/src/app/login/actions.ts:33-102` — действие входа само выстраивает порядок: проверка полей (`:39-46`), адрес клиента платформенной функцией (`:49-55`), `reserveSignInAttempt` (`:62-63`), очистка таблицы после ответа через `after()` (`:66-70`), `acquirePasswordCheck` и `release` (`:73-80`), `signInAccount` (`:77`), две cookie (`:82-87`), `settleSignInSuccess` (`:92`), разбор ошибок в четыре состояния `invalid`, `credentials`, `server`, `locked` (`:22-26`).
  - `/Volumes/T7/personal/ielts/src/lib/auth/throttle.ts:91-112,153-161,169-173`, `sessions.ts:33-65`, `passwordCheckGate.ts:4-28` — пять модулей, каждый знает свою часть порядка; ни один не владеет им целиком.
  - Эпоха сессии разнесена: запись `authEpoch + 1` и удаление сессий — `accounts.ts:152-154,200`, чтение и сравнение — `sessions.ts:43,59,86`.
  - `passwordCheckGate.ts:7-8` — счётчики на уровне модуля, состояние вне любого владельца процесса.
- Трение: порядок «посчитать попытку до проверки пароля, взять слот scrypt, открыть сессию, снять счётчик» нельзя нарушить без потери защиты (ACCT-03), но он записан только в вызывающем коде. Маршрут Hono унаследует эти шесть шагов; фоновая очистка, которую в ielts регистрирует `after()`, в api должна пройти через владельца запуска и остановки (17-07, `lifecycle.ts`), иначе её оборвёт `SIGTERM`. Адрес клиента в ielts берёт `@vercel/functions`; за Caddy его место займёт заголовок прокси, и правило доверия к нему сейчас нигде не записано.
- Тест удаления: если убрать действие входа, порядок шагов появится заново в каждом входе (учитель, ученик, смена пароля с проверкой старого). Модуль «вход» сконцентрирует порядок, пороги 5 и 20 и разбор исходов.
- Категория зависимости: local-substitutable (Postgres 18 в `dvlab_test`) плюс in-process (слот scrypt).
- Тесты сегодня: в dv-lab нет. В ielts тесты стоят на швах модулей (`tests/integration/sessions.test.ts`, `tests/integration/throttle.test.ts`, `tests/unit/password-check-gate.test.ts`, `tests/contract/auth-guards.test.ts`), а порядок шагов проверяет только e2e.
- Связь с фазой: расширяет (ACCT-01, ACCT-02, ACCT-03, ACCT-05).
- Сила: Strong
- Рекомендация: **в этой фазе** — модуль входа в `apps/api` с одним входом «попытка входа → исход», до планов, которые пишут маршруты, смену пароля и деактивацию. Интерфейс проектирует планировщик.

### 2. У контракта web и api нет владельца, а проверка границы запрещает общий пакет

- Файлы:
  - `apps/web/package.json:12-28` — ни одной зависимости `@dv-lab/*`; так задумано планом 17-02 (`17-02-SUMMARY.md`, проверка D4).
  - `.planning/phases/17-skeleton-on-the-server/17-10-PLAN.md:124` — шаг CI «в `apps/web/package.json` нет зависимостей `@dv-lab/*`»: запрещён любой пакет проекта, а не только `api` и `db`.
  - `.planning/phases/17-skeleton-on-the-server/17-CONTEXT.md:36,54` — D-07 запрещает код api в web (`route.ts`, `transpilePackages`, `paths`), а `api-types` удалён «до тех пор, пока не понадобится».
  - `deploy/caddy/Caddyfile:43` — `handle_path /api/*` срезает префикс: маршруты api без `/api`, браузер и web ходят с `/api`.
  - Эталон ielts: `src/lib/auth/cookies.ts:3,12,16` (имя cookie, параметры, форма токена) читают и `proxy.ts`, и `sessions.ts`; `routeAccess.ts:14-19` отвечает на «не вошёл» JSON 401, а `dal.ts:28-33` — редиректом на `/login?reason=expired`; `identity.ts:6-9` (шаблон логина, длина имени) нужен форме, api и скрипту первого учителя; `login/actions.ts:22-26` — четыре исхода входа с `minutes` для блокировки.
  - Страница обсуждения (`18-DISCUSS.src.html`): web смотрит только форму cookie, настоящую проверку делает api.
- Трение: фаза 18 впервые передаёт между процессами по HTTP имя и форму cookie, правила логина, исходы входа и ответ «кто я». Typed-клиент Hono запрещён (потребовал бы зависимость от кода api), общего пакета нет, а будущая проверка CI отвергнет и чисто типовой пакет контрактов. «Не вошёл» уже решается двумя способами (редирект в web, 401 в api), по одному правилу.
- Тест удаления: убрать общее место нельзя, его нет; сложность уже разошлась бы по `proxy.ts`, форме входа и api, и тем же путём пойдут контракты фаз 19-23.
- Категория зависимости: ports & adapters (собственные процессы по сети).
- Тесты сегодня: нет; в плане 17-10 только поиск строки `@dv-lab/` в манифесте web.
- Связь с фазой: расширяет (первый контракт web и api).
- Сила: Strong
- Рекомендация: **в этой фазе** — решение D о том, где живёт контракт (чисто типовой пакет без `pg` и без кода api, или явная копия констант в web), и, если выбран пакет, сужение проверки 17-10 до `@dv-lab/api` и `@dv-lab/db`. План 17-10 ещё не исполнен, поэтому правку проще внести до его запуска.

### 3. Состояние тестовой базы никому не принадлежит

  - `turbo.json:17-20` — у задачи `test` нет ограничения параллелизма; в `packages/db/package.json:9-13` нет скрипта `build`, поэтому `test` пакета `db` не ждёт сборку и может идти одновременно с `test` пакета `api` на одной базе `dvlab_test`.
  - `17-07-PLAN.md:99,164` и `17-09-PLAN.md:134` — тесты api запускают собранный `dist/server.mjs` с URL из `.env.test`; запуск процесса пишется в `shutdown.test.ts`, а `ws.test.ts` его переиспользует.
- Трение: фаза 18 добавляет три связанные таблицы (`accounts`, `sessions`, `sign_in_throttles`) и первые тесты api, которые пишут в них: вход, блокировка после пяти неудач, отзыв сессий при деактивации, переживание перезапуска api (критерий 3). Каждому файлу придётся самому знать порядок очистки таблиц с внешними ключами, получить роль миграций рядом с ролью приложения и не столкнуться с соседним файлом; в `api` файлы тестов по умолчанию идут параллельно.
- Тест удаления: убрать построчную очистку из тестов нельзя без общей замены; правило «чистая мигрированная база под ролью приложения, очистка под ролью миграций» повторится в каждом файле, который трогает таблицы, и в каждой следующей фазе.
- Категория зависимости: local-substitutable (настоящий Postgres 18, `dvlab_test` на домашнем сервере и в CI).
- Тесты сегодня: `roles.test.ts` проходит через интерфейс ролей; своей поддержки тестов у базы нет.
- Связь с фазой: расширяет.
- Сила: Strong
- Рекомендация: **в этой фазе** — поддержка тестов базы (сброс состояния, запуск собранного api и перезапуск) отдельным небольшим планом до планов, пишущих DB-тесты api. Интерфейс проектирует планировщик.

### 4. Пакет db не даёт приложению того, что нужно коду учётных записей

- Файлы:
  - `packages/db/src/connection.ts:28` — наружу выходит только тип `Database`; типа «база или транзакция» нет, а смена пароля и деактивация собирают несколько записей в одну транзакцию.
  - `packages/db/test/roles.test.ts:12-25` — разбор кода ошибки Postgres за `DrizzleQueryError` (код лежит в цепочке `cause`) существует только как приватная функция теста.
  - Эталон ielts: `src/lib/auth/accounts.ts:38-46` — `violatesUnique(error, constraint)` с проверкой кода `23505` и имени ограничения, вызовы на `:140,226`; `DatabaseSession` и `DatabaseTransaction` берутся из `src/lib/db/client`.
  - Страница обсуждения: два уникальных индекса (`accounts_active_login_uq`, `accounts_one_active_teacher_uq`), нарушения которых api должен различать (занятый логин против второго учителя, критерий 1).
- Трение: прямой перенос положит знание о драйвере внутрь модуля учётных записей `apps/api`; фаза 19 (ACCT-04, привязка к карточке, повторный импорт) и дальше повторят то же правило и либо импортируют его из модуля аккаунтов, либо скопируют.
- Тест удаления: если убрать классификацию ошибок, правило вернётся в каждого, кто пишет под уникальные индексы; но в фазе 18 таких потребителей два (создание ученика, скрипт первого учителя) и оба в одном модуле, так что сложность остаётся локальной.
- Категория зависимости: in-process (классификация ошибки) и local-substitutable (тип транзакции).
- Тесты сегодня: `roles.test.ts` использует приватную копию.
- Связь с фазой: расширяет.
- Сила: Worth exploring
- Рекомендация: **отложено** — перенести внутрь модуля учётных записей как есть; поднять в `@dv-lab/db`, когда появится второй потребитель (фаза 19, ACCT-04).

## Вне находок

- Speculative: эталонное ограничение попыток держит две блокировки строки `for update` на одну попытку (`throttle.ts:122-129`), а пул `createDb` — фиксированные 10 соединений с таймаутом 3000 мс (`connection.ts:23`), и тот же пул обслуживает проверку базы в `/healthz` (17-07). Поток попыток на один логин держит соединения в ожидании; в ielts, где каждый экземпляр функции имел свой пул, это не проявлялось. Учесть как условие приёмки плана ограничения попыток, не как отдельный модуль.
- Speculative: список переменных окружения повторён в `turbo.json:3`, `.env.example`, `deploy/env.example` и блоке `environment` compose; фаза 18, вероятно, добавит переменную доверия к заголовку адреса от прокси. Правило «какой URL базы» закрыто в 17 (D-06); здесь речь только о списке.
- Speculative: `createDb` собирает `drizzle` без `schema` (`connection.ts:24`), реляционный `db.query.*` недоступен; код входа пишется на `select().from()`, как в ielts, поэтому трения нет.
- Мёртвого кода в области нет: `apps/web` — заглушка, `packages/db` — один каталог миграции и одна таблица.
