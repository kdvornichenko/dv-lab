## Находки

### 1. Тип транзакции и разбор ошибок Postgres живут внутри `auth` (пересмотр находки 4 фазы 18)

- Файлы:
  - `apps/api/src/auth/sessions.ts:14-16` — тип `DbExecutor`; его уже берут `throttle.ts:8` и `middleware.ts:11`.
  - `apps/api/src/auth/accounts.ts:42-50` — `violatesUnique`; `:80` — `createStudent` принимает `Database`, а не транзакцию.
  - Копии обхода цепочки `cause`: `bootstrap-teacher.ts:61-69`, `request-context.ts:13-24`, `packages/db/test/roles.test.ts:12-16`.
- Трение: «создать аккаунт из карточки» читает карточку и вставляет аккаунт в одной транзакции, то есть работает через два модуля; `apply` импорта пишет пакет транзакцией и сообщает код ошибки, как `bootstrap-teacher`. Модуль карточек вне `auth/` вынужден брать тип из `auth/sessions.ts` и разбор `card_has_account` (23505 на частичном индексе) из `auth/accounts.ts` либо копировать. Второй потребитель появился.
- Тест удаления: если владельцем станет `@dv-lab/db`, исчезнут четыре копии и импорт `auth/sessions.ts` из чужих модулей.
- Категория зависимости: in-process (разбор), local-substitutable (тип транзакции).
- Тесты сегодня: только приватная копия в `roles.test.ts`; на `accounts.ts` тестов нет.
- Связь с фазой: расширяет. Сила: Strong.
- Рекомендация: **в этой фазе** — до планов модуля карточек и импорта. Классификатор нужен меньшему числу случаев: `account_already_linked` — проверка строки, идемпотентность импорта — `on conflict do nothing`; обязателен тип транзакции.

### 2. «Student» — два понятия под одним путём; список аккаунтов становится мёртвым

- Файлы:
  - `apps/api/src/routes/students.ts:33` (`GET /students` отдаёт аккаунты) и `:35` (`/:id/deactivate` с id аккаунта).
  - `auth/accounts.ts:97-104` (`listStudents`); `auth/account-rows.ts:13-19,35-45`.
  - `packages/contracts/src/auth.ts:30-39,77-89` — `createStudentRequest`, `StudentRow`, `StudentListResponse` описывают строки аккаунта.
  - web: `students-screen.tsx:26-32`, `deactivate-student-dialog.tsx:33`.
- Трение: по D-05 `/students/:id/account` принимает id карточки, а соседний `/students/:id/deactivate` — id аккаунта; под одним путём два вида id. Таблица `students` — карточка, а `createStudent` и `StudentRow` — аккаунт. `createStudentRequest` требует `displayName`, хотя по D-04 имя берётся из карточки.
- Тест удаления: после переключения у `listStudents`, `GET /students` по аккаунтам и `StudentListResponse` не остаётся вызывающих.
- Категория зависимости: in-process.
- Тесты сегодня: `packages/contracts/test/auth.test.ts:37+` на `createStudentRequest`.
- Связь с фазой: расширяет. Сила: Strong.
- Рекомендация: **в этой фазе** — убрать мёртвый список и развести имена аккаунта и карточки при переносе маршрутов (аккаунт ученика — `account`, карточка — `student`; деактивация идёт по id аккаунта под путём аккаунта карточки).

### 3. Правило имени ученика записано в четырёх местах

- Файлы: `packages/contracts/src/auth.ts:20-23` (`isDisplayNameLength`, не экспортирован); копии в `bootstrap-teacher.ts:45-46` и `create-student-dialog.tsx:112-115`; `packages/db/src/schema.ts:38` (CHECK 1..80).
- Трение: фаза добавляет схему карточки, форму, имя из H1 при импорте и CHECK у `students`. Имя карточки длиннее 80 символов уронит «создать аккаунт из карточки» на `accounts_display_name_ck` и вернёт 500; переименование карточки не меняет `accounts.display_name`.
- Тест удаления: один экспортированный предикат убирает три копии.
- Категория зависимости: in-process.
- Тесты сегодня: `auth.test.ts` проверяет нормализацию имени.
- Связь с фазой: расширяет. Сила: Strong.
- Рекомендация: **в этой фазе** — имя карточки берёт правило имени аккаунта из контракта (один экспортированный предикат). Расхождение двух копий имени (карточка и `accounts.display_name`) — отложено.

### 4. Правило «что входит в остаток» не имеет одного владельца

- Файлы: `.github/workflows/ci.yml:72-76` (contracts зависит только от zod); D-06 (core ни от чего не зависит); `numeric(7,2)` в D-08.
- Трение: точность уроков (2 знака), диапазон 15-240 минут и число знаков валюты нужны в zod-схемах contracts, в арифметике core и в CHECK базы. Остаток в списке (D-21) — агрегат SQL; правило «оплаты позже даты открытия; без открытия остаток не задан» core реализовала бы тоже. Фаза 21 добавит в это правило уроки.
- Тест удаления: core как владелец арифметики оправдана (предзаполнение, минуты в уроки и минимальные единицы нужны web, api и импорту); правило отбора без владельца разойдётся по местам.
- Категория зависимости: in-process (core), local-substitutable (агрегат).
- Тесты сегодня: нет.
- Связь с фазой: расширяет. Сила: Worth exploring.
- Рекомендация: **отложено**, с условием для плана: отбор оплат в остаток делает один модуль карточек в `apps/api`, core только считает. Вернуться в фазе 21. Зависимость web от core проверка CI разрешает.

### 5. Отдельный шов «разбор / запись» с двумя адаптерами для импорта не нужен

- Файлы: `apps/api/tsdown.config.ts:4`, `knip.json` (entry `apps/api`), `deploy/compose.yaml:87-98`; образец — `bootstrap-teacher.ts:15,76`.
- Трение: производитель один (md), потребитель один (база), шов гипотетический, интерфейс между шагами — zod-схема пакета. Реальный риск другой: если `apply` сам вставляет строки, правила записи карточки и оплаты окажутся в двух местах. Разборщик внутри образа api — код без данных, вреда нет.
- Категория зависимости: local-substitutable.
- Тесты сегодня: нет.
- Связь с фазой: расширяет. Сила: Speculative.
- Рекомендация: **отклонено** — отдельный порт и пакет не нужны. Условие: `apply` пишет через модуль карточек, так же как `bootstrap-teacher` пишет через `accounts.ts`.

## Вне находок

- Модуль карточек в `apps/api/src/cards` рядом с `auth/` разумен после находки 1. Ему можно импортировать только `auth/middleware.ts` (`requireSession`, `requireRole`, `readJson`, `noStore`) и `accounts.ts` для операций с аккаунтом; нельзя `sessions.ts`, `throttle.ts`, `sign-in.ts`.
- Коды 409 хранятся в одном списке `errorCodes` (`packages/contracts/src/auth.ts:45-59`), утечки нет.
- `apiRequest` (`apps/web/lib/api-client.ts:6`) знает только GET и POST; для удаления и правки его придётся расширить.

## Решения

Приняты по рекомендациям осмотра (`--auto`), не просмотрены владельцем; можно оспорить до планирования.

| id | название | решение | причина | модуль-владелец |
|----|----------|---------|---------|-----------------|
| 1 | Тип транзакции и разбор ошибок Postgres внутри `auth` | в этой фазе | второй потребитель появился (модуль карточек и импорт); убирает четыре копии и импорт `auth/sessions.ts` из чужих модулей | `packages/db` |
| 2 | «Student» — аккаунт и карточка под одним путём | в этой фазе | два вида id под `/students/:id`; список аккаунтов и его контракт становятся мёртвыми | `apps/api` (карточки) и `auth/accounts.ts` (аккаунты) |
| 3 | Правило имени ученика в четырёх местах | в этой фазе | имя карточки длиннее 80 символов роняет создание аккаунта; один экспортированный предикат | `packages/contracts` |

## Для планировщика

- Углубить `packages/db` (тип «база или транзакция» и классификацию нарушений уникальности) отдельным планом до планов модуля карточек и импорта; перенести копии из `auth/sessions.ts`, `auth/accounts.ts`, `bootstrap-teacher.ts`, `request-context.ts`.
- Развести имена аккаунта и карточки в маршрутах, контрактах и web при переносе `/students`; удалить `listStudents`, `StudentListResponse` и список аккаунтов вместе с переключением экрана.
- Экспортировать из `packages/contracts` предикат длины имени и применять его для имени карточки, аккаунта, формы и импорта.
- Модуль карточек в `apps/api/src/cards` владеет записью карточки, оплаты и отбором оплат в остаток; `apply` импорта и «создать аккаунт из карточки» пишут только через него; `packages/core` только считает.
