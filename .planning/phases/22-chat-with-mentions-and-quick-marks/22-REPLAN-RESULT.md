## Отклонения от предложений REPLAN-NOTES (с причиной)

1. `controller.store.refresh()` читателей не вызывает (перечитывает только незавершённые команды; читатели идут через `confirmedWindow` после применённой команды). Поэтому В7 сделан методом `refreshReaders()` контроллера.
2. Подтверждение «Moved to» из чата отправляет сервер, а не `controller.store.submit` в браузере: цель хранится на сервере и не приходит из тела запроса; владелец команд тот же; web-хранилище видит команду через `readUnresolved` после `store.refresh()`.
3. Отмена и возврат начавшегося урока без done разрешены по пункту (1) ведущей сессии; возврат выведен как обратное действие отмены (нужен для Undo «didn't happen»).
4. Проверка публикации ответа модели (22-13) удерживает число только рядом со словами учёта и денежными знаками, а не любую цифру: иначе педагогические ответы («Unit 5», «band 6.5») терялись бы. Деньги и счётчики — только блоками кода.
5. Существующие e2e и проверки ожидают перенос отмеченного прошедшего урока и разрез серии только с будущего вхождения; 22-02 и 22-18 правят их минимально, а падения из-за правил 24/25.1 (перенос требует Google) только перечисляют. 22-17 поднимает dev-стек для `yarn test:e2e` сам.
6. «По умолчанию прошедший урок списывается»: в коде списание делает только отметка (`done` всегда, `no_show` при `noShowDeducts`), неотмеченный урок ждёт отметки. План это правило не меняет; «восстановление баланса» = `no_show` → `none`. Автосписание неотмеченного урока — новое правило учёта фазы 21, в планы не включено.
7. Механика серий (вопросы 4 и 6) взята из 25.1 D-21: «all» начинается с `allFrom` — первой даты серии после последнего вхождения с `done` или `no_show` (22-07 добавляет вхождения с комментариями), не раньше окна синхронизации. Отмеченные вхождения не попадают в разрез и сохраняют ключ, отметку и остаток; `no_show` остаётся на старом времени. Новая серия начинается с `firstOnOrAfter(from, weekday)`: сегодняшний урок, перенесённый серией на уже прошедшее время, остаётся сегодня неотмеченным, а не пропадает на неделю.
8. Хранение настроек ассистента (В9): числовые настройки — колонки `teacher_settings` с DB-значениями по умолчанию, список моделей — `jsonb null` со списком по умолчанию в контракте (как `defaultTimeZone` / `SCHEDULE_TIME_ZONE`); тарифы редактируются учителем в записи модели; лимит входа проверяется в пределах 1 000..100 000 (граница базового тарифа Haiku 5.5), верхнюю границу выхода исполнитель берёт из документации. Переменная окружения для профилей моделей не используется.

Находки сквада, которые планы не меняют; формулировки находок — в выводе сквада у ведущей сессии.

## Что осталось неясным

1. **No_show при «all» и при правке серии из Google.** По 25.1 D-21 отмеченные вхождения остаются на старом времени, поэтому `no_show` с серией не переносится. Ответ на вопрос 6 говорит «без done»; перенос `no_show` вместе с серией требует переноса строки отметки, комментариев и квитанций чата на ключ новой серии. Планы делают по D-21; если `no_show` должен переезжать с серией, это отдельная доработка 22-18.
2. **Неотмеченные вхождения раньше последней отметки** остаются в старой серии на старом времени при «all» и при правке серии из Google (в Google они сдвинуты). Это следствие одной точки разреза.
3. **«This and following» с прошлого дня и End series с прошлого дня.** «This and following» принимает любую дату не раньше `allFrom`, в том числе вчерашнюю; End series по-прежнему не раньше сегодня. Вопрос не задавался, End series не менялся.
4. **Тарифы в форме.** Учитель редактирует цены сам; приложение не сверяет их с Anthropic. Значения по умолчанию прочитаны 2026-10-13.
5. **Оценка входа запроса (22-13).** Вход оценивается сверху числом байт UTF-8; для русского текста оценка в 5-6 раз больше реального числа токенов, поэтому при `maxInputTokens = 100 000` в запрос уходит примерно 17-25 тысяч реальных токенов истории. Для чата этого достаточно; больше контекста при том же лимите даёт только подсчёт токенов через API провайдера (лишний вызов на каждый запрос) — решение владельца.
