# 22-03 — Ревизия отметки урока

<objective>
Дать отметке урока ревизию, чтобы Undo из чата (22-09) не перезаписал более позднюю правку: «Done → No-show → Done» неотличимо по `kind`, ABA ловится только ревизией строки (ARCH-A3, 22-ARCH-REVIEW).

Executor model: opus (учёт, миграция, все писатели).

Purpose: CHAT-04 Undo отметки проверяет текущую ревизию (UD-04, D-03); Undo переноса из чата (22-10), снявшего `no_show`, возвращает отметку вместе с применением обратной команды, без участия браузера.
Output: колонка `revision`, одна функция записи `writeMark` для всех писателей, ревизия в блоках и ответе, `restoreMark` в журнале команд, скрипт проверки.

Писатели отметок в коде после 25.1 и 22-01 (полный список, проверить `grep -rn "lessonMarks" apps/api/src` перед правкой): `markOccurrence` и `markLesson` (`schedule/marks.ts`), `settleMarkAfterMove` (`schedule/marks.ts`, 22-01), `insertDomain` (`schedule/cut-apply.ts:165`, копирует отметку вхождения на новый одиночный урок при разрезе); этот план добавляет `restoreMarkAfterMove` (`schedule/marks.ts`). `inbound-apply.ts` отметки только читает. `keepCutLessons` в `series.ts` больше нет. Если `grep` находит ещё писателя, он переходит на `writeMark` в этом же плане.

Почему `restoreMark` в журнале, а не запись отметки чатом после проверки статуса: обратная команда применяется воркером календаря, когда Google подтвердил запись; если чат пишет отметку только при опросе статуса из браузера, закрытая вкладка оставляет урок без `no_show` и с вернувшимся остатком. Ревизия ожидается точно: `settleMarkAfterMove` исходного переноса растит её ровно на один, а пока команда ключа не завершена, другие записи отметки этого ключа отказывают (22-01, режим записи `historyEligibility`).
</objective>
