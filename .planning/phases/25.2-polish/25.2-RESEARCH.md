## Summary

Фаза большая (около 15 планов), но почти всё в ней ложится на уже построенные владельцы кода: модуль карточек `apps/api/src/cards`, чат `apps/api/src/chat` (инструменты, предложения `chat_actions` kind `change`, квитанции с Undo kind `note`), `packages/core` (правило остатка), маршрут чтения названий Google из PR 39. Новых подсистем три: блоки заметок со свободными именами (расширение `student_sections`), ревизия заметок (ход модели со своим режимом) и PWA с push (таблицы подписок, VAPID, планировщик в процессе api).

Главные расхождения заметок с кодом. (1) `studentBalance` не хронологический: он суммирует все оплаты и вычитает все уроки без порядка (`packages/core/src/balance.ts:28-42`), поэтому «тот же проход, что `studentBalance`» (D-22) требует новой функции core: хронологический проход по оплатам и урокам с покрывающей оплатой, остатком после урока, последней оплатой и началом серии долга. Ей же пользуются вкладка Lessons (столбцы Payment и Balance after), Overview (Last payment) и условие кнопки follow-up. Инвариант: итог прохода равен `studentBalance`. (2) Маршрут названий Google отдаёт только `{ title, day }` и запрашивает у Google поля `items(status,summary,start)`: для поиска по календарю нужны `end`, время и длительность. (3) Подавление уведомления «на переднем плане» нельзя делать в service worker: Safari отзывает подписку после трёх push без показанного уведомления. Подавлять нужно на сервере до отправки, по сигналу присутствия от открытой страницы. (4) `proxy.ts` перенаправит `/sw.js` и `/manifest.webmanifest` на `/login` без cookie, установка PWA сломается, если не расширить исключения matcher.

Блокирующих вопросов к владельцу нет: по каждой неясности ниже дана рекомендация, которую планировщик может принять. Нужны Design dude (иконки приложения, строка приватности для поиска по календарю, редактор промптов `/recap` и `/essay`, подтверждение, что перерисовки D-01 уже вошли в v101) и Server guy (VAPID-ключи в `/opt/dv-lab/env/api.env`, миграции, выкатка, проверка push на проде).

**Primary recommendation:** начать с волны «БД + зависимости + core-проход», дальше по паре «api-план, web-план» на волну; все изменения схемы блоков чата только расширяют union (старые сообщения в `chat_messages.blocks` должны продолжать разбираться).

### 6. PWA и push

**Состояние.** В `apps/web/public` только `robots.txt`, манифеста и service worker нет; `Dockerfile` web уже копирует `public` в образ [VERIFIED: apps/web/Dockerfile]. `proxy.ts` пропускает без cookie только `/welcome`, `/privacy`, `/terms` и matcher `'/((?!api|login|_next/static|_next/image|favicon.ico|robots.txt).*)'` [VERIFIED: apps/web/proxy.ts:7,14]: `/sw.js`, `/manifest.webmanifest` и иконки при истёкшей сессии получат 307 на `/login`. Манифест браузер грузит без cookie, поэтому без исключения установка не работает.

**Стек.** `app/manifest.ts` (`MetadataRoute.Manifest`, `display: 'standalone'`, `start_url: '/'`, иконки 192 и 512) и `public/sw.js` с регистрацией `navigator.serviceWorker.register('/sw.js', { scope: '/', updateViaCache: 'none' })`; отправка — `web-push` с `setVapidDetails` и `sendNotification`; заголовки для `/sw.js`: `Cache-Control: no-cache, no-store, must-revalidate` [CITED: nextjs.org/docs/app/guides/progressive-web-apps, обновлено 2026-07-30]. Push работает в iOS 16.4+ только для приложения, добавленного на Домашний экран, Safari 16 на macOS 13+, Chromium, Firefox [CITED: там же]. `app/manifest.ts` не нарушает шаг CI «Web and api boundary» (запрещён только каталог `apps/web/app/api`) [VERIFIED: .github/workflows/ci.yml:53-78]. Service worker без обработчика `fetch` (офлайна нет).

**VAPID и секреты.** Переменные api читает только `loadConfig` (`apps/api/src/config.ts`), образец необязательного блока — `loadCalendarConfig` с `enabled` [VERIFIED: config.ts:97-122]. Рекомендация: `PUSH_VAPID_PUBLIC_KEY`, `PUSH_VAPID_PRIVATE_KEY`, `PUSH_VAPID_SUBJECT` (без переменных push выключен, как чат без `ANTHROPIC_API_KEY`); subject — `https://`-адрес (например `APP_ORIGIN`), не `mailto:` с личной почтой (CI `Repository hygiene` отклоняет личные адреса). Публичный ключ отдаёт api (`GET /push/config` или поле в `GET /settings`), а не `NEXT_PUBLIC_*`: образ web собирается в публичном CI, ключ не должен вшиваться при сборке. Секреты лежат в `/opt/dv-lab/env/api.env`, который compose уже подключает к api (`env_file` с `required: false`) [VERIFIED: deploy/compose.yaml]; имена добавить в `deploy/env.example`.

**Планировщик.** Процесс api один (compose), образец периодической задачи — `createHousekeeping` (`setInterval` + `unref`, `runOnce` без наложения, `close` в `lifecycle.manage`) [VERIFIED: housekeeping.ts:17-52; server.ts:135-147]. `pg-boss` 12.37.1 уже в зависимостях api (очередь календаря), но для минутного тика не нужен: дедупликация уникальным ключом в `push_deliveries` (`insert … on conflict do nothing` как захват) защищает от повторов при перезапуске и наложении контейнеров на выкатке. «Скоро урок»: тик раз в минуту, окно уроков `[now, now + 120 min]` из доменных строк (`loadScheduleRows` + `scheduleWindow` + исходы, отменённые и перенесённые-призраки исключены), ключ = ключ вхождения + `startsAt` (перенесённый урок напоминается по новому времени), отправка, если `startsAt - minutes <= now < startsAt`. «Скоро платить»: проверка раз в 5-10 минут по `listCards` + `balanceState`; переход в Pays soon/None left/Owes из взведённого состояния даёт одно уведомление и снимает взвод; возврат выше порога взводит снова; при первом запуске (нет строки состояния) только записать состояние без отправки, иначе все текущие должники получат push в момент выката. Архивные и «не задан» не участвуют (`paysSoonList` фильтрует `active` [VERIFIED: lessons.ts:80-87]). Ответы push-сервиса 404/410 помечают подписку `revoked_at`.

**Передний план (D-40).** WebKit: подписка создаётся с `userVisibleOnly`, push без показанного уведомления считается тихим, после трёх тихих подписка удаляется [CITED: webkit.org/?p=12945; webkit commit «Enforce silent push quota»]. Service worker обязан вызывать `showNotification` внутри `event.waitUntil` на каждый push. Подавление — на сервере до отправки: открытая страница шлёт сигнал присутствия (экран и ученик, раз в 30-60 с и на `visibilitychange`) в api, планировщик не шлёт, если сигнал свежий и экран совпадает (Schedule для урока, профиль ученика с вкладкой Payments для оплаты). Хранить присутствие можно в памяти процесса api (перезапуск безвреден). Рекомендация — подавлять только на том же устройстве (сигнал несёт endpoint своей подписки); не блокирует.

**Переход по тапу.** `notificationclick`: найти окно через `clients.matchAll({ type: 'window', includeUncontrolled: true })`, `focus()` и `navigate(url)`; `navigate` работает только у окна под контролем SW, поэтому в `activate` вызвать `clients.claim()`, иначе — `clients.openWindow(url)`. URL строит сервер из фиксированных частей: урок — `/schedule?week=<date>&lesson=<ref>` (прибытие `ScheduleArrival` построено), оплата — `/students/<id>?tab=payments`. Только фиксированные слова и непрозрачные id (правило v88 п.50).

**Локальная проверка.** `localhost` — безопасный контекст, SW и push работают на `http://localhost:3000` в Chrome и Firefox без HTTPS; iOS проверяется только на проде (HTTPS + Домашний экран).

### Pattern 2: Правило «только добавление»
```ts
export function isAddition(before: string, after: string): boolean {
	const lines = (text: string) => text.replace(/\r\n/g, '\n').replace(/\s+$/u, '').split('\n').map((line) => line.trimEnd())
	const old = before.trim() === '' ? [] : lines(before)
	const next = lines(after)
	let at = 0
	for (const line of next) if (at < old.length && line === old[at]) at += 1
	return at === old.length && after.trim() !== ''
}
```

### Anti-Patterns to Avoid
- **Подавление push в service worker:** Safari отзывает подписку; подавлять на сервере.
- **Сужение union блоков чата:** старые `chat_messages.blocks` перестанут разбираться в `blocksOf()`.
- **Второй расчёт остатка в web или в chat:** остаток после урока считает core, вызывает только `cards`.
- **Поиск по календарю через Google `q`:** ищет и в описании, D-23 — только название.
- **`NEXT_PUBLIC_VAPID_*`:** ключ вшивается в образ при публичной сборке.
- **Правка 31 места `scroll-fade`:** один глобальный fallback.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Web Push (VAPID JWT, aes128gcm) | свой `node:crypto` | `web-push` 3.6.7 | Криптография и форматы трёх push-сервисов |
| Состояние фильтров в URL | свой парсер query | `nuqs` (D-30) | Валидация, debounce, `clearOnDefault` |

## Common Pitfalls

### Pitfall 1: Сужение контракта блоков ломает историю чата
**What goes wrong:** удаление `chatSuggestionsBlock` из `chatBlock` или смена `sectionKind` на строку с другими правилами — старые сообщения не проходят разбор.
**Why it happens:** блоки хранятся в jsonb и разбираются zod при каждом чтении.
**How to avoid:** схемы блоков только расширять; web перестаёт рисовать Suggestions, контракт остаётся.
**Warning signs:** 500 на `GET /chat/conversations/:id` для старых разговоров.

### Pitfall 2: «Тот же проход, что studentBalance»
**What goes wrong:** граница и остаток после урока считаются на несуществующей хронологии.
**Why it happens:** `studentBalance` суммирует без порядка.
**How to avoid:** новая функция core; dev-check сравнивает её итог с `studentBalance` по всем dev-карточкам.

### Pitfall 3: Тихие push в Safari
**What goes wrong:** подписка iPhone исчезает после трёх подавленных уведомлений.
**How to avoid:** `showNotification` всегда внутри `waitUntil`; подавление на сервере.

### Pitfall 4: Массовая рассылка Pays soon при выкате
**What goes wrong:** при первом тике все текущие должники получают push.
**How to avoid:** первая оценка без строки состояния только записывает состояние.

### Pitfall 5: Манифест и SW за proxy
**What goes wrong:** 307 на `/login` для `/manifest.webmanifest` и `/sw.js`.
**How to avoid:** расширить исключения matcher (`sw.js`, `manifest.webmanifest`, иконки).

### Pitfall 6: publish-gate удерживает ответ с датами событий
**What goes wrong:** ответ про найденные события не публикуется.
**How to avoid:** выдача инструмента с ISO-датами и `HH:MM`, чтобы `learnWhen` их выучил.

### Pitfall 7: Ревизия и предложения против ревизии карточки
**What goes wrong:** запись даты ревизии в `students` увеличит `revision` и сделает `stale` все открытые предложения по карточке.
**How to avoid:** дата ревизии в отдельной таблице M5.

### Pitfall 8: Восстановление удалённого слова
**What goes wrong:** повторное добавление слова из Removed падает на `student_terms_term_uq`.
**How to avoid:** при совпадении `lower(term)` со строкой `removed_at is not null` — восстановить строку.

### Pitfall 9: Stale dev-check миграций
**What goes wrong:** `schedule-db.ts` ожидает 8 папок миграций, их 32 и станет больше.
**How to avoid:** план БД обновляет проверку.

### Pitfall 10: Параллельные правки контрактов
**What goes wrong:** api-план и web-план одной волны правят `packages/contracts/src/chat.ts`.
**How to avoid:** контракт меняет api-план функции; web-план той же функции — в следующей волне.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Подмена endpoint на внутренний адрес (SSRF) | Tampering | Принимать только `https:`; не следовать редиректам; при желании allowlist хостов push-сервисов |
| Утечка endpoint из логов | Information disclosure | Не логировать endpoint и ключи |
| Названия событий Google у провайдера модели | Information disclosure | Строка приватности в Settings (D-23), только название/дата/время/длина, без описания, без логов |
| Prompt injection из текста заметок и событий | Tampering | Текст — данные (как в `student_notes`); записи заметок решает сервер по diff, деньги и карточка — только через Confirm |
| Устаревшая запись блока | Tampering | Ревизия блока, `409` |
| Глубокая ссылка из push с данными | Information disclosure | Только фиксированные слова и id в URL (v88 п.50), в тексте уведомления — имя и время, без сумм |
