## AR-01 — Один module разрешения local time и даты

**Приоритет:** обязательное решение для A/C, до UI.

**Наблюдение:** zonedInstant делает два offset passes и возвращает Date без результата gap/fold. Общая зона — `SCHEDULE_TIME_ZONE = 'Asia/Ho_Chi_Minh'`. Window/next и balance используют общую дату. [VERIFIED: packages/core/src/zoned.ts:92-98] [VERIFIED: packages/core/src/schedule.ts:3-15,205-239,254-301] [VERIFIED: packages/core/src/balance.ts:19-36,49-75,97-120]

**Риск:** если каждый caller исправит только форматирование, API и browser получат разные local-date правила. Gap будет выглядеть как сохранение другого времени; weekly next может исчезнуть.

**Решение:** core принимает zone явно. zoned module возвращает candidates и задаёт отдельный startOfZonedDay. schedule применяет policy: ручной gap — отказ; recurring gap — пропуск; fold — первый instant. SeriesRule хранит timeZone; display/accounting zone передаётся отдельно. Не добавлять external package, собственную tz database или параллельный resolver в web. Детали — RESEARCH §4–5.

**Deletion test:** если убрать этот module, обработка переходов и календарной даты появится в create/move/series, Today, карточках и web. Ответственность необходима. Универсальная calendar engine или interface с единственным искусственным adapter не нужны.

**До → после:** implicit global zone / Date без outcome → explicit zone / определённое разрешение local time.

**Владельцы изменения:** core zoned/schedule/balance и их реальные callers. Cut/end можно выделить в связный schedule-series module для сохранения file limit, без механического деления.

**Interface-strength check:** caller знает только validated wall date/time/zone или instant/context; не знает число offset passes, поиск перехода и правила Intl.

**Доказательство:** существующая move journey через реальный create/read/move; gap/fold, weekly до/после перехода, next lesson после пропущенной недели. Обязательные assertions — exact instants и сохранённые zones. Это план проверки, не PASS.

## AR-02 — Настройки и данные одного ответа принадлежат одному snapshot

**Приоритет:** обязательное решение для B, до API/UI waves.

**Наблюдение:** текущий TeacherSettings — `{ paysSoonLessons: number }`; PATCH требует paysSoonLessons. В БД paysSoonLessons notNull без default. Schedule содержит generic readSnapshot с `isolationLevel: 'repeatable read'`, `readOnly: true`. [VERIFIED: packages/contracts/src/settings.ts:6-12] [VERIFIED: packages/db/src/schema.ts:313-323] [VERIFIED: apps/api/src/schedule/rows.ts:331-333]

**Риск:** zone-only PATCH может потерять Pays soon или упасть при первом insert. Отдельные чтения settings и facts могут показать новый label на остатке старой зоны. Две date-sensitive записи могут пересечь смену настройки.

**Решение:** settings module владеет partial upsert, прочтением контекста и account-row lock. Вставка заполняет отсутствующее поле текущим продуктовым default; update меняет только предоставленное. expectedDefaultTimeZone защищает запись local dates от stale формы. Generic snapshot helper перенести в существующий DB connection module; в ответе вернуть данные и authoritative zone/asOf одного snapshot.

**Deletion test:** без settings owner правило partial update/lock повторится в schedule/card/Today routes. Generic snapshot является небольшим механизмом транзакции, а не новым business facade. Не создавать global settings singleton/cache.

**До → после:** потребитель отдельно читает settings и facts → один aggregate response с явным time context.

**Владельцы изменения:** contracts settings/response metadata, DB connection export, API settings, затем schedule/cards/Today collectors. Одинаковый lock order account → existing domain row.

**Interface-strength check:** core получает значения, web получает self-consistent response; ни один из них не должен знать SQL или момент отсутствия settings row.

**Доказательство:** existing Today/settings journey — zone-only, Pays-soon-only, конкурентные PATCH, первая строка, stale запрос, отказ другой роли; затем reload и одинаковые accounting facts на экранах. Прямой SQL не заменяет public API assertion.

## AR-03 — Cut/end переводят границу, а новое weekly rule хранится в новой зоне

**Приоритет:** обязательное решение для A/C и dependency фазы 24.

**Наблюдение:** core cut принимает `SeriesChange = { from: string; weekday: Weekday; startTime: string }`; API загружает exceptions/marks непосредственно от input.from. CutLesson уже содержит `originalOn: string`; успешный результат — `{ kind: 'ok'; oldEndsOn: string; newRule: NewSeriesRule; lessons: CutLesson[] }`. API сохраняет detached lessons и копирует marks. [VERIFIED: packages/core/src/schedule.ts:332-340,365-370] [VERIFIED: apps/api/src/schedule/series.ts:20-52]

**Риск:** дата from новой зоны не равна natural date старой. Разовый перевод нового weekday/time в старую зону нарушит обещанное wall time после DST. Перепутанный cutoff может отрезать прошлое или потерять moved/marked хвост.

**Решение:** from/lastOn интерпретировать в current default; получить boundary instant, затем old natural cutoff. Загрузчики получают этот cutoff. Существующий natural prefix остаётся в старой серии. Новый rule получает введённые weekday/time и current default timeZone напрямую. Finite end переводится через exclusive instant старой границы. Detached lessons сохраняют старые instant, mark и creation zone. D-17 для single move не ограничивать.

**Deletion test:** без core cut/end module календарный перевод и сохранение хвоста появятся в двух API mutations и UI preview. Не добавлять второй cut interface в sync или отдельную модель «display series».

**До → после:** одинаковая строковая шкала дат для UI и rule → явные display boundary / old natural date / new rule zone.

**Владельцы изменения:** core cut/end result, API series loader и insert adapter, contracts timeZone, Whole series form/preview. UI preview обязан использовать тот же смысл boundary; серверный результат авторитетен.

**Interface-strength check:** pure cut success остаётся указанной формы; к NewSeriesRule/CutLesson добавляется timeZone. Persisted IDs возникают только в API. У cut tail originalOn связывает новый lesson с old series occurrence для будущего sync mapping.

**Доказательство:** existing move/marks journeys — from по другую сторону полуночи, today guard, finite end, DST до/после, moved/marked/cancelled tail, старый natural prefix, отсутствие двойного вычета. Политику re-key detached хвоста не маскировать утверждением о вечных IDs.

**Dependency 24:** default change не reschedule; cut создаёт новый seriesId и detached lessonIds. 24 проектирует mapping в существующей транзакционной точке insert. Outbox/Google calls в 21.1 не добавлять.

## AR-04 — Browser preference и time formatting имеют одного владельца

**Приоритет:** обязательное решение для A/B и TZ-05.

**Наблюдение:** useSecondZone живёт вместе с picker; normalizer сейчас отвергает Vietnam и подставляет default second. Сохранённые ключи — `'dv-lab.schedule.second-zone'`, `'dv-lab.time-zones.favorites'`; событие — `'dv-lab:time-zones'`. [VERIFIED: apps/web/components/app/time-zone-picker.tsx:17-22,24-61] Settings и schedule импортируют этот общий owner. [VERIFIED: apps/web/app/(app)/settings/_components/settings-screen.tsx:5-8,21-31] [VERIFIED: apps/web/app/(app)/schedule/_components/schedule-screen.tsx:7-16]

**Риск:** отдельный новый settings store разойдётся с schedule. Optimistic swap меняет вторую зону при отказе. Сравнение labels/offsets смешивает разные IANA zones.

**Решение:** сохранить store/keys, параметризовать нормализацию текущей main identity. Canonical identity validation принадлежит contracts; short labels — web formatter. После authoritative success выполнить collision swap и notification; cancel/error не пишут storage. Ответы экранов несут собственную main. Existing TimePair/formatters получают явную зону; recurrence в browser не раскрывать.

**Deletion test:** если убрать shared owner, normalization/collision/sync появятся в settings и schedule. Отдельный глобальный preferences framework избыточен.

**До → после:** Vietnam-special fallback / фиксированный main label → explicit main identity / shared reconciliation.

**Владельцы изменения:** time-zone-picker, time-zones, schedule-format, TimePair, settings dialog и реальные display callers. Existing overlap layout остаётся; DST не требует нового календарного layout.

**Interface-strength check:** форма знает saved/pending values и результат save; детали localStorage, aliases и событий скрыты в owner. Форматтер знает instant+zone, но не fetch/settings.

**Доказательство:** existing Today/move journeys — collision и alias, cancel/error/retry, tabs/reload, main отличается от browser zone, два fold instants доступны, Created in только в деталях. UI-review не выполнялся; пункты 233–255 UI-SPEC совместимы с этим решением. [VERIFIED: .planning/phases/21.1-default-time-zone/21.1-UI-SPEC.md:233-255]

## AR-05 — Сначала расширить существующий settings recovery

**Приоритет:** обязательное решение для D до runtime.

**Наблюдение:** existing recovery читает/восстанавливает accountId, paysSoonLessons, updatedAt и проверяет JSON equality. Зоны в текущем snapshot нет. [VERIFIED: e2e/support/data.ts:143-183]

**Риск:** зелёный journey может оставить изменённую account zone; последующие сценарии и ручная работа будут использовать другое состояние. Восстановление только Pays soon не доказывает cleanup новой фазы.

**Решение:** расширить тот же recovery snapshot зоной, сохранить различие «строки не было», точный updatedAt и accountId. Capture выполнить до первой mutation. Восстанавливать только в уже разрешённом fixture lifecycle; не расширять SQL/delete полномочия. Scenario behavior проверять через публичный UI/API. Новую fixture infrastructure или отдельный unit suite не создавать.

**Deletion test:** убрать recovery — значит перенести сохранение/восстановление в каждый journey и сделать ownership неясным. Это существующий необходимый module.

**До → после:** snapshot части settings → snapshot всех полей, которые новая journey может изменить.

**Владельцы изменения:** e2e/support/data.ts и вызывающий existing fixture; сценарии today/move/marks.

**Interface-strength check:** scenario не знает SQL и путь private state; fixtures предоставляют bounded lifecycle. Не заменять оригинальный saved snapshot уже изменённой строкой.

**Доказательство:** inspectable before/after fingerprint и restore status; сценарии дают original exit; evidence не содержит пользовательских данных. Runtime запускается только после передачи DB/ports ownership.
